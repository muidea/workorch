## 字段与场景的判断规则

每组合同逐项回答：

| 核对项 | 可接受依据 | 不能作为依据 |
| --- | --- | --- |
| 当前需求 | 明确的正常或失败/恢复场景、输入与结果消费者 | 将来可能用、字段越全越好 |
| 必要性 | 删除会丢业务输入、破坏身份/反证/并发/恢复/审计或改变消费者行为 | 名称相似便视作重复；所有上下文均打包 |
| 充分性 | 对本场景可唯一绑定输入、owner 事实、结果及下一步允许行为 | DTO 可以编码、hash 可以重算 |
| 条件参数 | 触发条件、缺失/空值语义明确，非法组合拒绝 | 所有请求都携带所有参数；用默认值掩盖缺失 |
| 数据用途 | 业务输入、权威绑定、历史事实、诊断、展示用途明确 | 诊断驱动状态迁移；历史 PASS 视作当前 PASS |
| 异常分支 | duplicate/stale/unknown/超时/取消/重启/停机适用分支有证据 | 未找到回执等同未执行；失败等同可重发 |
| 信息边界 | 消费者只接收本用途材料，原材料在受限 owner 边界完整保全 | 用摘要替代原文；原始诊断/凭据进入公共投影或模型上下文 |

“覆盖所有对应场景”以当前明确支持的交互为边界。未支持的场景必须明确拒绝，不能猜选；不要求为未知的未来需求
预加字段。实际验收须同时核对发送端、接收端、返回绑定、持久 cut point 和最终消费者。

## 已深入核对的主体链与字段用途

### 1. 创建与精确确认

入口：[creation](../../internal/modules/kernel/workspace/pkg/events/definition_authoring_creation.go)、
[confirmation](../../internal/modules/kernel/workspace/pkg/events/definition_authoring_confirmation.go)。

- 创建的 RequestID 绑定原创建，WorkspaceID 定域，Input 保全业务输入；Title/Description 是 Workspace 元数据，
  两个目录是服务端已解析路径。它们一起参与原 creation hash；恢复不能用另一份今日草稿替代。
- 确认命令只提交 WorkspaceID、InputHash、DerivationPermitID、ProposalHash、SpecificationHash 和 ExpectedWorkspaceRevision。
  这六项分别绑定 Workspace、原输入、原派生、原提案、所审规格和首次 CAS。界面不回传一份可修改的正式 Goal/DoD，
  不传 caller-selected eligible，不附带执行 intent。
- 返回 Goal/DoD 是物化结果；不表示已 eligible，也不表示当前没有 Run。精确原 journal 负责丢回复后的恢复。

### 2. 显式准备与内部观察续接

入口：[Workspace command/result](../../internal/modules/kernel/workspace/pkg/events/activation_preparation_command.go)、
[Application consumer](../../internal/modules/application/workorchd/biz/activation_preparation.go)、
[observation continuation](../../internal/modules/application/workorchd/biz/activation_preparation_observation.go)。

| 字段 | 来源/消费者及必要用途 | 防干扰边界 |
| --- | --- | --- |
| WorkspaceID / RequestID / ExpectedWorkspaceRevision | owner 作用域、原操作幂等/恢复、首次并发门禁 | 公共准备请求不附全 Workspace、今日 bootstrap 或用户 PASS |
| CompilationSource | Workspace 返回原归档的 detached typed 值，Application 用其纯编译原操作 bootstrap | `json:"-"`，不进入公共 HTTP，不是调用方可回传的成功凭据 |
| ObservationRequired | 首次接纳后的续接消费者决定是否发观察；恢复分支拒绝该标记 | 短期控制返回值，不是持久 readiness |
| SkillHubPlan | Workspace 先封存效果计划，Application 执行精确原计划 | 不允许调用方换目标或在 replay/recovery 重发 |
| ProviderDefinition | 原选择声明，Application 用以指定 exact target | 不能用 owner 默认模型掩盖原声明错误 |
| 原 Facts 与 Reason | Workspace 核验来源/原操作并存历史；无材料也需表达 unavailable/not_saved | Reason 不能替代 Facts 授 credit；有材料时校验其一致性 |

`Facts + Reason` 不能机械地合并为一个布尔值：实际观察到阻塞与根本未保存观察是不同场景。
不过这条续接目前是 blocked settlement，仍不能证明全 required 成功结算已经实现。

### 3. File 最终重观察与进程身份

入口：[File events](../../internal/modules/blocks/file/pkg/events/preparation_revalidation.go)、
[File observation](../../internal/modules/blocks/file/pkg/preparation/observation.go)。

- 重观察 Scope 包含原 Workspace/request/payload/revision、两目录、资源 refs 和配置 targets；结果完整 echo Scope，
  逐项核对数量、顺序、原 bytes/版本。payload hash 不代替原值核对。
- OwnerEpoch 防止跨 owner 重建复用；TokenID 标识本次观察；StartedAt/ObservedAt/ExpiresAt 限定读取完成及观察年龄。
  三者不能合并成一个“已检查”标志，30 秒也不是文件不变租约。
- QueryPreparationEpochCommand 为空是合理的：查询进程级 epoch，无需附加业务正文、文件路径或 Workspace 参数。

### 4. 原执行意图与未知结果恢复

入口：[Workspace recovery](../../internal/modules/kernel/workspace/pkg/events/execution_recovery.go)、
[Run receipt query](../../internal/modules/blocks/run/pkg/events/execution_intent_receipt.go)、
[reserve-before-forward](../../internal/modules/kernel/workspace/biz/execution_intent.go)、
[original settlement](../../internal/modules/kernel/workspace/biz/preparation_settlement_internal_event.go)。

- 恢复输入仅 WorkspaceID、RequestID、Kind，原 payload 身份来自 owner 持久 reservation；不要求重送今日 bootstrap。
- Run 查询带原 PayloadHash，绑定同一个 RequestID 下的确切输入；结果 echo 身份、ObservedAt 和可空原 Receipt。
  Receipt=nil 是 unknown，不能推导“未执行”或重新 forward。
- 新 fresh Restart 必须先 reserve CAS；CAS loser/replay 不 forward。普通成功响应也不能冒充持久原回执。
  完整 reservation/receipt 配对后才由 Workspace 私有 reducer 结算。

### 5. Registry、Memory 与模型缓存

入口：[Skill](../../internal/modules/blocks/skill/pkg/events/preparation_catalog.go)、
[Memory](../../internal/modules/blocks/memory/pkg/events/preparation_inventory.go)、
[MCP Registry](../../internal/modules/blocks/mcpregistry/pkg/events/preparation_snapshot.go)、
[LLM cache](../../internal/modules/blocks/llm/pkg/events/catalog_cache.go)、
[Application cache consumer](../../internal/modules/application/workorchd/biz/activation_preparation_catalog.go)。

- 完整库存服务于缺失、歧义、关联和原声明反查，不能先过滤成“已选项摘要”再声称库存完整；选择后的模型/公共投影
  只携带其用途需要的材料。当前性和授权仍是独立事实。
- LLM 的 Target 条件可选，nil 明确代表该 owner 冻结默认值；若有 Budget，须绑定 exact target 或冻结默认。
  Configuration 是非秘密选择声明；Catalog 的 model/operation/context/output/reasoning 等各有能力选择或预算用途，
  不应统一强制所有模型提供推理专用参数。
- OwnerEpoch、ObservedAt、FetchedAt、ExpiresAt 分别表示配置生命周期、观察时间、缓存取得时间和缓存期限；
  不应简化成一个 fresh 布尔值，也不能推导 provider 授权。

### 6. Runtime effect、批准与正式交付

入口：各 capability `pkg/events/operation.go`、
[Run lifecycle](../../internal/modules/blocks/run/pkg/events/lifecycle_messages.go)、
[Result delivery](../../internal/modules/blocks/result/pkg/events/lifecycle_messages.go)、
[Approval](../../internal/modules/blocks/approval/pkg/events/messages.go)。

- sealed operation 保留完整 operation、payload hash、execution scope，部分 owner 还需要 catalog/revision/policy。
  这些是执行前精确反证；不另收一份可漂移的自由 command 来选动作。SSH/MCP 的 endpoint/secret 由 owner 解析。
- Approval 的 Principal 与不可变 AuthorizationContext 证明身份和批准范围；ResolutionContext 仅保留审计，
  不能合并成通用 context 后丢失这一区别。
- ResultMaterial 保留已判原结果、逐项 assessment/evidence/artifact 等，排除调用方指定的正式 Result.State/生命周期字段。
  Result owner 派生正式身份和 ACK；capability receipt 不自行产生 CWI credit。
- 这些字段的结构及局部门禁不代表 Runtime 终态链已通过公开正例；当前 ImplementationWork availability 仍关闭。
