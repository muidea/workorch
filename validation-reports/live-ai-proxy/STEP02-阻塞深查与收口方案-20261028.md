# STEP02 阻塞深查与收口方案

日期：2026-10-28。性质：只读分析及候选实施方案，**不是已落地设计合同或收口通过记录**。分析基于 `c76a4c573e54b91e57a86737cadcec31c7441092` 源码和 2026-10-27 清空数据后的真实验证原证据。本轮没有新模型调用、生产业务写入、配置变更或 Run 启动。

## 结论

需要处理两个独立层面：

1. 提案要求模型抄写 owner 的长 hash；本次模型错抄资源 hash，原严格绑定门禁正确拒绝。建议用版本化 authoring 请求／结果合同将机器身份绑定留给 owner，模型只返回语义工作结果。
2. 默认软件开发模板要求真实变更回执、Git 快照和正式 Result 逐项索引，但封存 Profile 没有将对应 typed 消费者绑定到这些模板 DoD。模型保留三项 `UNVERIFIED` 有实际依据，需要补齐来源绑定和组合证明声明。

局部消费者代码已经存在，不能把“默认 Profile 没接入”写成“整个系统没有实现”；也不能把已有消费者测试通过写成默认模板完整集成通过。

## 一、直接阻塞的证据链

### 请求与输出

- `authoring_request.go:37` 从 sealed derivation 生成动态输入，包含正确的 input/template/resource 身份及完整 Profile。
- 输入字段名为 `inputHash`、`templateHash`、`resourceSnapshotHash`；输出要求 `InputHash`、`TemplateSnapshotHash`、`ResourceSnapshotHash`。命名转换与多个摘要并存增加了模型的机械抄写任务，但不能据此断言是唯一诱因。
- `definition_authoring_mapping.go:82` 同时精确核验 protocol 和三个身份。本次原始 provider 文档的输入及模板身份正确，仅资源身份不匹配；错误是 `sealed_identity`，不是 JSON 结构解析失败。
- 当前 mapping schema 的这些身份字段只约束为 string，没有动态精确枚举值。ai-proxy 的 `ResolveProviderClient()` 又明确设置 `JSONSchemaResponse: false`；`responsesTextForRequest()` 因而不请求原生 schema 格式。模型实际依赖提示合同，本地严格校验才是最终门禁。不能未经网关能力确认就把该配置改为 true。
- 上轮实际上游请求 wire 未归档，本轮源码重建也不能替代实际上游请求的原文证据。可以确定的是：原始响应确实有错，现行请求构造代码提供了正确值。

### 无外发的隔离复核

通过 Go `-overlay` 将临时测试映射入目标测试包，源文件与日志均位于 `/tmp/workorch-validation/step02-analysis-20261028/`，没有往项目源码写入测试文件。

1. 用归档 owner 前像和原 provider payload 调用原 parser，稳定复现 `sealed_identity`。
2. **仅在 detached 内存对象中**将资源身份对齐，用于隔离后续校验路径；未改 provider 原 bytes、原 owner、completion 或 ledger，也未生成可接纳凭据。
3. 其余 canonical mapping 编译、封存 Profile 结构验证和声明来源适用性验证通过。3 个 `UNVERIFIED` 保持不变。
4. 三个来源均有 `software-dev / * / dodItem` 普通声明选项。这证明“选项存在”，不证明该声明足以履行回执或终态义务。
5. 源码重建的动态请求为 78951 bytes，C0/C3 两个分区；请求使用静态 mapping schema。此重建只用于分析，不是原始 live 请求 attestation。

所以当前已定位的首个阻塞就是资源身份回显；后续语义审查结果仍未知，不能从离线结构校验推定六审会通过。

## 二、三项 UNVERIFIED 的实际缺口

归档模板的 DoD 与 Profile 分别和当前默认配置逐项相等。封存 `software-dev` Profile 只有 `acceptanceDimensions`、`coverageDependencies`、`deliverableExpectations` 和 `evidenceRequirements`，所有 evidence requirement 都没有 `LineageAssertions`。

| 原始模板来源 | 当前适用声明 | 欠缺内容 | 优先复用的既有消费者 |
| --- | --- | --- | --- |
| `derived-dod:template:000003`：变更最小、相关且有 capability-owner state_change receipt | `dodItem/*`，required kind 为 validation | 普通相关性验证与真实变更回执之间没有本条可消费的组合绑定；`deliverable/source_change` 自己的 state_change 声明不能被当成本条声明 | `terminal_owner_operation_receipt` 或适用的 execution receipt consumer，精确绑定真实来源、owner、kind、variant 和 effect |
| `derived-dod:template:000004`：真实 git/write add/commit 快照与 commit 引用 | `dodItem/*`，required kind 为 validation | Git 声明在 `deliverable/version_control_snapshot`，没有本条的最终快照证明责任 | `terminal_owner_snapshot`，`runtime/terminal-material-proof/v2`，Git commit 与真实普通验证来源精确绑定 |
| `derived-dod:template:000013`：正式 DoD 逐项 evidenceRefs 并可追溯 | `dodItem/*`，required kind 为 validation | 普通文件检查不能消费尚未产生的正式 Result 逐项索引 | `terminal_result_evidence_index`，`runtime/terminal-material-proof/v1` |

`authoring_verification_options.go` 当前仅输出 ProfileID / EvidenceRequirementID / Scope 三字段，只解决来源适用性。`SpecificationVerificationApplies()` 也验证来源与合并规则，不对自然语言义务进行自动语义证明。这是职责边界，不能把更多自报 DECLARED 当作缺口已闭合。

现有 `runtime_validation_proof_composition.go` 支持普通验证消费者和 lineage consumer 的职责组合；终态消费者与 snapshot 代码也有对应实现。它们需要明确的 Profile opt-in、原来源和绑定，不能因为函数存在就自动启用。

## 三、建议实施顺序

### 收口 A：身份由 owner 绑定，模型专注语义结果

建议审定新的版本化 STEP02 authoring 合同，而非改写 v1 的语义：

1. reserve 前由 owner 封存 workspace/input/template/resource/target、阶段、review kind、proposal 身份及所选 wire contract 的版本／hash。
2. 模型输出保留语义 mapping、具体声明或审查结论；机器身份由 owner-managed request envelope 关联，不再要求模型重新生成长 hash。派生、提案和六审采用一致的身份责任分工，各阶段仍保持不同的闭合语义 schema。
3. 只允许原已签发 permit 对应的真实 completion 进入编译；接收时重验精确快照、阶段、原 proposal、配置、预算、去重和请求合同。缺失、错 scope、迟到、重复冲突及合同漂移均拒绝。
4. 原 provider bytes 单独完整保存；typed result 的 owner 身份与 provider 原文明确区分。不得把 hash 填入原 JSON 后声称是 provider 返回，也不得为旧失败创建第二次调用许可。
5. 独立审查仍只读取同一封存 proposal，完整覆盖 Required 集合；不读取其他审查结论，不省略六审或人工确认。
6. v1 归档继续按原合同解释；新版本只用于明确的新事务。版本选择进入请求账本，重启恢复不能按当前代码猜版本。

主要落点：`specifications/{authoring_request,schemas,authoring_document,derived_acceptance}.go`、Workspace authoring request/ledger/mapping/confirmation、对应 typed events 与查询投影。它属于启动前 authoring 流程，不需要增加 Runtime 状态机或执行入口。

若先交付保持 v1 的小补丁，可统一输入输出字段名、提供独立精确回显区并细化错误 path；这只能提高可诊断性及降低抄错概率，**不能作为系统性解决或稳定通过的退出条件**。

### 收口 B：为三项原义务封存精确的组合证明职责

1. 在 Template/Profile 层显式声明原模板条目的证明绑定，保留原义务全文。普通 validation 负责最小性、相关性、内容和行为；typed receipt、最终 Git snapshot、正式 Result index 分别负责其 owner 事实。
2. 使用 sealed template 内的精确条目来源映射到确认后 DoD；同时核对原文身份。当前 materialization 顺序为 user → template → generated，用户验收条目数会改变 `dod-NNN`。因此不能在默认 Profile 里硬编码 `dod-003/004/013`，也不能在核心中用关键词猜选。
3. 来源解析和 Profile 编译必须是同一条纯逻辑，由提案、独立审查、owner completion、确认恢复、admission 与 activation 重用并独立复核。不能只给 LLM 添加一份解释而 owner/activation 仍使用旧 Profile。
4. 动态声明选项补充该来源真实可用的 consumer refs、契约版本和消费时点，引用已有 sealed Profile 规则；不附加未来事实、receipt 或结果。仍允许事实不足时返回 UNVERIFIED。
5. File 回执消费者必须覆盖模板允许的实际 owner operation 形态。现有规则要求 exact kind/variant，不能用一条 File-write 规则声称覆盖任意 mutation，也不能将多个备选操作误写成每种都必须发生的 AND。若需要支持操作集合，先限定并审定闭合集合选择语义，再实现和测试。
6. 终态义务延后到真实不可变材料产生后核验。现有依赖图中最终 Git snapshot 在 DoD、validation report 之后；不能让普通 DoD 提前等待它，否则形成循环。SM-2 保留普通证明门禁，SM-3 保留真实 dispatch/receipt 和组合职责，SM-4 消费对应终态材料；SM-1 生命周期不变。
7. 每项 ordinary criterion 必须仍有真实可执行验证；lineage 不能取代工程行为或当前验收。终态快照与 Result 消费者的存在也不能提前授予 satisfied/credit。

主要落点：默认模板/Profile、精确模板来源编译、`authoring_verification_options.go`、Workspace admission/confirmation 与既有组合消费者的接线。优先复用既有消费者，只补现有类型不能表达的来源／操作集合边界，不扩大到整套 Runtime fullflow 优化。

### 收口 C：验证完成后再进入下一步 live

先完成以下无收费验证：

- 新 wire/request/ledger 的来源绑定、错误 scope、stale/late/duplicate、合同版本漂移、重启和失败不可重发反例；原始 payload bytes/hash 保持独立。
- 新旧合同严格分离；schema、local parser、owner completion、确认恢复采用同一所选版本，不能出现宽松 fallback。
- 0/1/多个用户验收条目，以及模板条目重排、原文变更、Profile 漂移和冲突场景的来源映射；三项 guard 不能误挂到其他普通 DoD。
- consumer 缺失、借用其他 scope、未知 operation variant、错 receipt、旧 snapshot、悬空 evidenceRefs、漏原文和缺终态材料均阻塞。
- 现有 ordinary validation 与 typed guard 为 all-of；明确测试无执行循环，并保留失败终态的忠实交付语义。
- 使用明确暴露 consumer 职责的本地 fixture 完成 STEP01→STEP02→确认边界验证。fixture 仅证明流程和拒绝行为，不声称真实模型质量或实际终态执行已经通过。

然后以可核对源码输入和二进制哈希的产物部署，在保留旧失败的前提下显式创建新验证事务，再对相同完整 PRD 进行一次真实 STEP02 验证。退出条件为：42 条原始验收完整保留；提案接纳；六审完整且 PASS；全部原义务具有适用的真实能力声明；无自动重发、无正式 Goal/DoD 提前物化、无 Run。确认、准备及执行仍按后续步骤分别验证。
