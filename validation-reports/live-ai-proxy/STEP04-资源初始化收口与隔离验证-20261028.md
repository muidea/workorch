# STEP04 资源初始化收口与隔离验证

日期：2026-10-28。性质：代码收口及验证记录，不是现行设计权威。

本轮补齐上一次真实 AI Proxy 验证发现的主体缺口：缺失托管配置和项目 Skill 目录此前只能等到执行阶段才准备。
现已接通独立资源初始化的 Workspace → File → 持久 journal → HTTP → Web 流程；初始化后显式新检查消费真实观察。
没有部署、重启或清空现有 8090 服务，没有重新派生真实候选，也没有发起真实推理或 embedding。

## 已落地行为

- `initialize-resources` / `recover-resources` 只接收 Workspace 路径、原 requestId 与 expectedWorkspaceRevision。
  owner 精确读取原封存链，从实际模板和 Workspace 声明重建完整目标与正文；自洽 hash 不能增加目标或改变正文。
- 原请求、完整配置前像、Soul sidecar、creation/preparation epoch 与计划先 CAS 持久化，再向 File 派发。
  scoped repository 在锁内读取真实 sidecar；保留完整配置绑定，不因 metadata 拆存而忽略 Soul 配置。
- File 只创建缺失托管配置和项目 `.agents/skills`。Linux 使用 pinned/no-symlink/no-cross-mount 子路径、
  完整写入和 fsync、原子 no-replace 发布；保留已有配置、用户覆盖、符号链接及内容冲突，不自动 merge 已有文件。
- 每次派发前持久消耗预算，每操作最多 4 次、最多 16 个操作；丢失回复不恢复预算，普通重复请求不重做。
  显式恢复只重做原有的收敛式创建；所有旧 attempt、结果和原失败准备历史保留。
- 原配置 JSON bytes、大整数、文件前后像和原错误保全在 owner 私有存储。原错误超过 4096 bytes 时明确记录
  未保存原因及原字节数/hash，不截断、不把已知失败变成 unknown。公共 GET 只返回有界身份、状态及已消耗次数。
- 未完成初始化阻止新准备检查和 fresh execution reservation。它不改变 SM-1～SM-4 reducer，不授予 ready/M3/执行权。
- Web 增加显式初始化和恢复入口；POST 后 GET 对账，保留原身份，关闭重开从 owner 找回未完成操作。
  切换 Workspace 拒绝迟到响应，不用浏览器持久化，不自动初始化、检查、Skill 安装或执行。

规范入口已同步：`docs/50-product-interface/service-api.md`、Workspace 与 File owner readme。

## 部署后复验顺序与剩余边界

1. 用户编译部署，保留当前已确认 Workspace、候选、规格和原失败检查数据。
2. 打开原 Workspace 准备页，只读确认当前 owner revision，再点击“显式初始化准备资源”。
3. 如果回复丢失，只读对账或显式恢复原初始化身份，不换请求号。
4. 初始化完成后点击“显式检查准备”，核对新的 File 前后像和实际 global/project SkillHub → Skill → MCP 来源。
   原失败检查仍是历史，不回填通过。
5. Provider 仍需真实授权证据；本轮未补造该证据，也未开放收费 probe。ready/M3 及 STEP05 执行消费不在本轮收口范围。

本轮方案代码及隔离验证已完成；当前真实部署上的对应结果仍待部署后 live 复验。
