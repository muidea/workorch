## 未通过：生产 Web 完成回执合同

生产浏览器打开/只读刷新准备页均显示 **Error: 准备完成身份无效**，没有正常展示 10/10、completion 与 currentValidity；不能引用后端事实替代 Web 通过。

已定位的充分原因：

1. `internal/pkg/workorchmanagementcontract/startup_preparation.go:47` 将 `PreparationEpoch uint64` 标为 `json:"preparationEpoch,omitempty"`。首次合法准备 epoch=0，真实 HTTP attempt 因而没有 preparationEpoch 属性。
2. `web/workorch-console/src/startupPreparation.ts:283` 对含 completion 的 attempt 要求 `a.preparationEpoch !== 0` 时拒绝。实际取值 undefined，触发“准备完成身份无效”。
3. 现有组件 fixture 显式填写 preparationEpoch:0，没有经过生产 Go DTO 的 JSON 编码，因此未覆盖真实成功 wire。

直接以本轮真实响应执行当前 `validatePreparationView`，复现同一错误；仅在 detached 内存副本补入明确零值即通过。未修改生产响应、持久记录或浏览器数据，未以此授 credit。与到期无关，零值省略同时影响原 observed 及后续 stale 回执。

### 最小收口与复验方案

保持首次准备必须 epoch=0 的严格门禁，修正生产 wire 对合法零值的表达，优先由 Go DTO 显式输出 preparationEpoch；不要用前端把任意缺失值默认为可信零来放宽 completion 身份。同步核对旧记录及非首轮/非零 epoch 的拒绝边界，不扩展执行授权。

增加真实 Go JSON 序列化断言，并将该实际编码形态交给 Web validator/组件作为成功 fixture，覆盖 completed+observed、completed+stale 与合法历史 M3；保留缺失/错误 epoch、错误 request/hash/revision、伪造 completion 的拒绝用例。修复后部署，复用本 Workspace 原已确认封存及原 completion，通过只读 GET/浏览器刷新复验；无需清库、重新确认或重跑收费六审。若要证明新的当前 observation，再单独显式新检查，不能恢复已过期观察或新增 Run。

本轮不修改生产代码，不自动部署修复。STEP05、真实进程重启、实际网关转发归档及多 Workspace live 并发不在本轮已通过清单。
