## 1. MCP：缺的是准备观察合同，尚未实际连接失败

### 原归档与调用链

本次精确选中 `mcp-lsp-bridge` 和9个工具能力，选择无错误，Registry 双读相等。`PreparationMCPSelectionCompilation.BlockedReason()` 对成功非空集合明确返回 `mcp_selection_compiled_connection_pending`；这不是从某个失败的 MCP 响应推导出来的。

Application 的准备观察只读取 Registry，再由 Workspace 封存选择与原裁决。`blocks/mcp/pkg/events` 当前只有六个 Runtime ingress：capabilities、admissibility、operation feasibility、semantic proof feasibility、reconciliation、execute，没有准备连接命令或当前连接事实查询。

已有 `ProbeOperation` 对 HTTP 只检查 endpoint 结构，对 stdio 检查 command/path 等本地前提；按现行合同不得启动进程、联系 endpoint 或产生 operation receipt。管理页 tools/resources/prompts 查询也只是把 Registry 中的 Server metadata 转为 DTO，不能替代实时发现或连接证明。

MCP execution owner 内已有 stdio 会话、协议 initialize、owner-local 环境引用解析和生命周期排空能力，可复用其技术实现，但现有 execute 入口必须有真实 Run、sealed operation、ExecutionKey/Fence 和 grant；准备阶段不能伪造这些身份去借用该入口。

### 当前可以排除和不能排除的原因

已能排除“本次 Registry 选择报错”“准备检查实际尝试连接并返回失败”“Provider 配置阻断了该项”。前次排查 shell 能找到 lsp-bridge/gopls，只能证明排查环境安装了程序，不能据此证明 Workorch 服务进程的 PATH、权限、精确配置及握手全部正确。

尚未经过真实连接验证的内容包括：服务进程实际启动环境、托管路径解析、协议握手、选中工具是否由服务真实发布、会话退出与持续有效性。当前没有数据可将其中任何一项认定为实际故障。

### 与原阶段范围的冲突

归档 STEP04 计划 §1/§3/§5 和实施前审阅稿 §1 明确排除“启动 MCP/外部 live probe”，同时要求真实连接事实；在当前既没有已有连接事实查询、也没有历史可消费连接回执的情况下，默认非空 MCP 正例必然阻塞。它符合当前负向门禁，却不能完成主体正向验收。

若严格保留该边界，只能接入 MCP owner 已有的可信连接事实；当前未找到这样的生产接口，不能直接宣称这条路线已经可用。若要继续验证这个默认非空 MCP 的正例，需要单独明确准备连接观察的范围，不能以普通“只读查询”名义偷偷启动进程。

### 最小收口建议

在现有 `blocks/mcp` 内增加独立于 Runtime execute 的版本化准备观察能力，由显式准备操作触发，Workspace 负责接纳身份和预算，Application 负责跨 owner 编排。参数只携带精确 Workspace/原 request/payload、声明及 Registry/配置绑定、owner 可核验路径来源和时间预算；不传凭据、session 或 repository。

结果应包含真实观察的 server/能力绑定、owner/process/session 代次、开始/结束时点、协议结果、工具发布匹配、关闭结果及有限失败分类；原始响应/错误由 owner 受限保存，公共层只展示必要分类和引用。一次性探测后关闭只能证明历史时点握手，不能假称当前仍存在连接；需明确采用短期观察有效性，还是由 owner 管理的会话有效性，不能混用。

协议级 `initialize` 与业务工具 `lsp_initialize` 是不同操作。准备观察不调用 `lsp_initialize`、`lsp_repair` 等业务工具，不授予派发或验收 credit。工具清单核对也不证明未来每次工具调用一定成功。

普通重复、GET、SSE 和恢复不得重发观察；派发结果不明时保留原身份及预算，按 owner 的精确原结果查询恢复，不能通过新 request 绕过未知。此为建议的新合同，未在本轮实施或运行。

## 2. Bootstrap：真实总容量与 authoring 接受能力不一致

### 原归档纯诊断结果

本轮使用正式 file repository codec 和生产 `PreparationCompilationSource.Model()`，通过 `/tmp` Go overlay 在原编译点增加计数，仅离线读取原归档，不修改生产源码/数据，不运行 owner 外部操作。

| 结构 | 数量 |
| --- | --- |
| dodItem | 67 |
| deliverable/source_change | 1 |
| deliverable/validation_report | 1 |
| deliverable/version_control_snapshot | 1 |
| WorkItem / Definition focus / mutable focus | 各70 |
| acceptance slice | 19 |
| 原封存 MaxFocuses | 64 |

诊断仍为 `bootstrap_structure_rejected`，原诊断122 bytes，SHA256 `a3aaf32b051af31617e5631982123c1b6e275f4495d1ab9f04f01227b42f29bb`，与上一轮一致。

在不授予编译成功的前提下，额外单独执行了焦点编译末尾的 implementation-work、lineage、verification 三项纯合同校验，均未报错。它只缩小当前归因范围，不代表越过容量门后整个 bootstrap 或 Runtime 一定通过。

### 为什么调 slice 或配置无效

`runtime_focus_compiler.go` 为每条工作项生成一个独立 focus，再按总数与封存 MaxFocuses 比较。slice 只是分组；现有测试明确断言10条工作项分3组仍有10个独立焦点。因此当前19个 slice 已证明“有分组”，继续调组大小不能把70降到64。

`runtime_acceptance_slice.go` 将 `RuntimeAcceptanceFocusMaxCount` 固定为64，并要求策略 MaxFocuses 不得超过它；`runtime_repair_ledger.go` 的 convergence policy 也复用该上限。仅把模板 JSON 的64改成70会被策略校验拒绝；仅提高代码常量而保留当前封存策略64，也仍会拒绝这份历史合同。

authoring 派生允许128条 additional items，Specification 允许更大的要求/义务集合；当前 admission 核验 all_of、谱系、Profile proof closure 及 implementation-work 可用性，但没有与实际焦点编译共享的总容量预检。因此这份逻辑合法的候选能六审通过并 eligible，直到 STEP04 才遇到容量冲突。eligible 本来就不保证资源 ready；这里应补的是跨阶段容量一致性和早期诊断，不把 STEP03 合法确认误判为越权启动。

### 最小收口建议

1. 抽取 owner-neutral 的纯覆盖布局/容量预检，计入所有真实必需来源和 Profile 交付项。authoring 候选数量确定后尽早检查，正式 admission 再独立核验；不能等待付费六审全部完成或资源初始化后才提示。
2. 统一 authoring、Profile、bootstrap 和 Runtime 的有界容量合同。若产品要支持本次67条 DoD，应制定支持至少70个总焦点的版本化容量方案并验证存储、请求字节、预算和重启成本。它不是简单配置刷新，也不能取消上限或合并各项验收 credit。若保留64上限，系统必须尽早准确阻塞，并说明总量与构成。
3. 将泛化的“configure bounded acceptance slices”诊断改为准确分类与必要的计数/上限信息；公共层无需原始规范全文或配置。
4. 保留所有原 Goal/DoD 与证据。若容量方案需要改模板/封存策略，走正常新候选/新确认链，不修改当前 immutable StartupInput，不自动删减6条 DoD，不把旧准入当成新策略的人工确认。

不建议本轮优先引入焦点分页、只物化部分 Definition 或重新拆成多个 Workspace：那将涉及 SM-2/SM-3 权威和恢复合同，明显大于当前容量一致性问题。

## 3. STEP04 主体：还缺成功 final CAS 和 M3

源码已明确确认：

- `WorkspacePreparationAttemptState` 仅有 accepted、blocked、failed、unknown，无成功准备态。
- `reduceWorkspacePreparationBlocked` 固定保存 blocked；assessment 的 checks_passed 只是一份清单摘要，不改变 operationState。
- `CheckStartupPreparation` 先完成负向结算，再从原归档编译完整 bootstrap，将结果放入当前 POST 的独立 compilation 响应。没有把“完整编译成功＋全部 required 真实有效＋no-Run final fence”合取为成功提交。
- `WorkspacePreparationFence` 保存 creation/preparation epoch 和 fresh intent 历史，但没有 M3 completion 记录。现有精确 no-Run final fence 是成功流程的前提材料，不能冒充完成回执。

这与现行 service-api 对 v2 的负向边界一致，属于尚未交付的计划主体；不能通过给 Web 改成功文案或把 HTTP200 当 ready 解决。

建议在新的版本化准备事务中，先保存接纳与外部观察义务，收集真实 owner 材料并纯编译，再由 Workspace owner 在最后一个 CAS 中独立反查全部 required、精确 seal、revision/epochs、观察时效、无未决 reservation 和完整 Run 历史，形成准备成功与唯一历史 M3。完整编译必须成为该合取的真实输入及独立可复算来源，不能由调用者上传 PASS/hash 获得授信。

同时补齐成功响应丢失后的原请求重放、CAS竞争、accepted/unknown 中断、真实 owner 重建、M3唯一性、后续 stale 保留历史及 Web 分轴展示。旧 blocked attempt 保持原结果，新检查使用新身份；不能在 GET/recover 时升级旧历史。

STEP05 的 Start/Restart 完整准备回执消费仍保持独立。本轮发现成功结算缺失，不意味着应把创建 Run 或执行权限接入 STEP04。
