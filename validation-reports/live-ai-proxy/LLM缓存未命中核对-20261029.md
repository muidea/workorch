# LLM 缓存未命中核对（2026-10-29）

## 结论与边界

本轮核对的是 STEP02 规格派生、提案及六类独立审查，不是 Runtime loop。Workorch 的 authoring 缓存规划和 Responses 消息渲染存在明确缺口；当前 AetherRelay Codex 路径还存在与这种请求形态组合后逐请求改变缓存身份的情况。不能仅凭输入 token 数接近就认定应当命中。

本轮只做归档读取、源码检查与离线函数验证，没有调用真实模型、改配置、改部署数据或启动 Run；没有修改 LLM 生产代码。工作树另有此前 MCP 协商修复，不能将其当作本次缓存修复。

## 已核实事实

1. `authoring_request.go` 的 `authoringSpecificationCommand` 仅生成 C0 固定规格合同与 C3 大型请求 JSON。Goal、候选、Profile 等可共享资料均位于 C3。LLM owner 的 generic `completeProvider` 路径未调用 Runtime 的 `attachProviderCachePlan`，这批审计中的缓存策略及稳定前缀 hash 均为空。
2. `http_provider.go` 的 `responsesRequest.Input` 是 string。`responsesInputForRequest` 将稳定前缀和动态内容拼成单条字符串；字符串中的 `[user]` 不构成协议消息边界。请求结构没有 `prompt_cache_key` 或 `prompt_cache_options`。
3. 从原 owner 归档通过正式 codec、生产 review command 和 HTTP renderer 重建六审。六份重建 wire 的长度均与原 audit 的 requestBytes 一致；这不是原请求抓包，也不构成原 wire 字节相等的证明。六审的固定 C0 均为 3,412 bytes，SHA256 相同；input 约 187 KB，与首审的公共 input 前缀为 41,154 bytes。变化的 kind 位于约 41,146 bytes，后面约 146 KB 共享资料无法继续作为连续公共前缀。bytes 不能直接换算为 cacheable tokens。
4. AetherRelay 当前源码 `6cbc042`：`conversationAnchorHash` 不从 scalar input 取锚点；Codex 路径对没有会话、锚点、显式 key 的请求回退 requestScope，生成逐请求变化的缓存 key。离线调用真实函数已复现，显式稳定 key 则保持稳定。但未取得远端本批请求的实际 route、account、转发 key 或部署版本，故该项是条件性网关诊断，不能写成已证实的远端路由事实。
5. Workorch 的 cached_tokens 使用 int 接收，缺失与明确为零无法区分，且未解析 cache_write_tokens。原公共 audit 没有缓存读取字段；六审没有原始成功 wire 可供回溯，派生/提案 wire 因超过存储边界明确标为未保存。因此本轮不能独立证明原上游明确返回 cached_tokens=0。当前 AetherRelay 源码区分缓存用量 unknown 与已知零，但尚未取得这些远端事件的原始用量。

## 缓存规则核对

本轮实际读取的 [OpenAI Prompt caching 文档](https://developers.openai.com/api/docs/guides/prompt-caching) 对 GPT-5.6 及以后模型采用消息结束位置和 breakpoint 的规则，最小可缓存长度为 1,024 tokens。单条不断变化的 user 文本没有为中间固定资料留下独立可复用的消息结束位置，长公共字符串前缀本身不等于可命中缓存。

缺少 prompt_cache_key 本身不足以单独解释所有未命中；但网关逐请求生成不同 key 会隔离复用身份。0% 是读取比例，也不能据此断定没有缓存写入。缓存还受实际模型映射、组织、处理地域及过期等条件影响。当前 Codex 适配会移除部分缓存私有参数，不能承诺仅追加一个参数即可解决。

## 建议收口顺序

1. Workorch authoring 先形成可审计的共享快照与阶段输入分区，保全全部原 Goal、候选、Profile、规格及六审独立性；把每类审查的变化内容置于末尾独立消息。共享业务原文仍是待审资料，不能升级为系统指令。
2. LLM owner 统一编译缓存计划和实际请求审计，Responses adapter 保留真正的 typed 消息边界，并传递与精确公共内容及目标绑定的稳定缓存身份。requestID、时间、review kind 和凭据不得进入共享缓存身份。不减少六审、不引入本地答案缓存。
3. 区分读取/写入用量及字段是否存在，缺失显示 unknown；记录实际渲染的稳定前缀身份，用确定性 mock 覆盖相同快照、变化尾部、前缀漂移及用量缺失。
4. 确定性验证通过后，核对部署网关实际 route 与转发 key，再用有界真实请求验证读取/写入和费用。不要在缺少这些证据时承诺命中比例；本轮不默认重跑收费六审。
