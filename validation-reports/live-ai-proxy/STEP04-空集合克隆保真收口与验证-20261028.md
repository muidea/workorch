## 原因和最小修复

前一轮生产失败及原始证据见《STEP04-资源初始化生产复验与CAS阻塞定位-20261028》。持久 JSON 的嵌套空数组解码为非 nil 空集合；repository Get 的 typed payload Clone 原先遇到长度 0 即返回 nil，改变了返回前像。初始化在去除 journal/revision 后严格比较完整 Workspace，因而拒绝合法 reservation，尚未发生 File 效果。

本次仅修改 `workorcheventpayload` 的 `cloneFields`、`cloneValues` 和 `CloneSlice`：区分 nil 和非 nil 空集合，并保持完整独立所有权。没有改变 JSON／canonical／hash 算法、完整 metadata 比较、scope、revision、配置、封存链、budget、fence 或 CAS 门禁；没有改写历史，没有增加迁移或自动重试。Workspace owner readme 补充这一克隆前像合同。SM-1～SM-4 的状态机及授权迁移均未修改。

## 定向证明

- 基础测试覆盖 nil、预留容量的空集合、嵌套对象／数组／null、中文原文；Clone 后逐层变更不能污染原输入，原 JSON 和 canonical 保持一致。
- 初始化组合测试经 Application/EventHub 形成真实 blocked 检查及 execution inputs，然后关闭 owner、驱逐该隔离路径的进程内 decoded cache，再从真实 JSON 冷加载。首次 reservation／settlement 成功，revision 精确增加 2、一次 File attempt；旧准备检查、封存证据、authoring、StartupInput、admission 与 Run 边界保持。
- 直接解码实际持久文件核对嵌套空集合，避免比较两个同样失真的 Clone；普通重放、恢复和再次冷加载均返回同一完成结果且不重写 owner 字节。
- 仅以 Go overlay 恢复旧三处克隆判断时，基础测试失败，组合测试在初始化处重现 `conflict`。该负例退出码 1 为预期反证；正式修复版通过。

冷加载补强曾暴露旧 typed fixture 的模板数值 kind 与 JSON 入口不同，导致模板快照哈希在首次真实解码后变化。已在**测试封存之前**让夹具模板经过生产 JSON 输入形态，未修改生产 hash／decoder，也未放宽原封存校验。同进程 owner reopen 不能替代该冷加载或下述真实进程重启证据。
