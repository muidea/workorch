## 4. 收口顺序与责任

### R1：先打通普通开发生产主链

**目标：在原 CWI 下合法、持续地修改实现，而不是借终验失败修复权限承担一般开发。**

主要位置：默认 Profile/模板、Profile 编译与 Workspace admission、`runtime_implementation_work_policy.go`、orchestrator 的 `implementation_work_*` 事务、File owner scope/feasibility，以及现有公开 fullflow 和终态消费者。

1. 先明确首个支持的能力组合。用 Profile 声明 owner、operation、selector、最大工作轮次/目标数、fresh observation/validation 和输入保护；声明绑定 exact CWI，不携带已选动作或预授 credit。
2. 尽量复用已有工作协议：owner 观察 → SM-2 scope/purpose/working binding → SM-3 独立候选/feasibility/sealed dispatch → 真实 effect receipt → 同 CAS 结轮及资源失效 → fresh observation → 下一轮或 terminal purpose。
3. 逐项核验尚未证明的 terminal 消费链。工作历史只能证明已发生行为；当前资源验收、reviewed input、Git 交付快照、完整义务及正式 Result 必须分别取得真实证据。现有代码可复用，不默认重新设计全部消费者。
4. 默认软件开发 Profile 只对适合开发的义务声明工作策略；综合验收、只读或其他类型义务不能无条件授予文件修改。具体项目路径和能力拆分留在项目上下文/owner 观察中。
5. availability 从“声明均不可执行”变为“精确已支持组合可执行，其他仍阻塞”，与默认声明及公开正反例一起交付。不能删除 gate、统一返回 true，或让测试走私有 startup 绕过正常 admission。

退出要求：现有 `TestImplementationWorkPublicAuthoringFullFlow` 经正式默认 Profile、创作、确认、activation 跑通；有明确两轮义务的原 CWI 取得两次有意义的独立工作效果，仍保持零终验 credit；fresh 终验、Git、Result/Workspace/Run 三 ACK 完整。保留原十分钟判据、unsupported 反例及预算，不改成 skip/expected failure。

该用例现在明确在“默认 Profile 未封存 dodItem implementationWorkPolicy”处失败；这是本轮发现的生产缺口与早期 CI 之间的直接对应，不应继续只当作测试落后于实现。

### R2：打通输入生成与有界修订

**目标：生成足以检验原准则的输入；审查拒绝时，可在明确权限与额度内修订输入，不能降低准则。**

主要位置：Profile 输入用途声明、Shell adapter 的观察/生成合同、File 输入写入边界、LLM projection、`validation_input_review.go` 及对应 typed runtime contract。

1. 保留 `56632340` 的真实项目上下文与 exact `SourceObligationChecks`。逐项映射应覆盖生产能力、边界与原验收范围；文件存在、build 成功、测试数量和测试名不能替代行为断言。具体语言/HTTP/SSE 检查留在 adapter、Profile、项目上下文中。
2. 明确新生成、原样复用、受权修订三种用途。ready binding 的 review 可以合法拒绝旧输入；不能因看见旧文件就假定其语义已经合格，也不能因输入旧就自动删写。
3. 增加版本化、Profile 明示的有界输入修订合同。最小绑定包括：Run/Definition/原 CWI/原 check、完整 review 来源与结论、原输入集合的完整内容身份、owner 当前 revision 与可写范围、替换/补充方式、新输入版本、原事务身份及额度。路径/hash 换代不能刷新 Run + 原 CWI/check 的额度。
4. 完整 conflict、纯 omission、inconclusive 保持不同事实；前两者只能在声明支持修订时进入新路线，后者沿既有有界事实澄清。缺失、歧义、unknown、stale 或超额阻塞，不伪造 rejected Shell receipt，不借 schema correction 或 physical retry 额度。
5. SM-2 封存修订来源/commitment；SM-3 由 File 执行精确、有限写入；随后 owner fresh re-observe 和新的独立审查。一致后才能进入原 ordinary validation。旧输入 bytes、原审查、原拒绝与全部账本历史保留，重启按同一操作对账。

此项改变了现行“conflict 终态失败”的合同，是候选合同扩展；不能作为单纯 prompt 修复静默上线。需要同步当前规范、typed contracts、owner readme 和状态机测试，再实现接线。

退出要求：保留旧弱输入的反例；合法修订能够得到新的独立 consistent review 并实际执行；重复、前像漂移、跨 CWI/Workspace、越界、回复丢失、重启与超预算均不能多写、多调用或获得 credit。

### R3：组合验证真实失败后的实现修复与后继推进

复用已有 confirmed repair 及 `56632340` 的交接修复，不新增一套通用“失败就改文件”机制。

- 前提必须是已独立审查的一致输入实际执行后产生真实失败；完整失败诊断经 owner 精确归属，缺失或相邻未知失败保持阻塞。
- 精确封存实现修复 commitment、目标前像及允许写面。不能改验收输入来消除实现失败，也不能把 review conflict 冒充行为失败。
- File accepted receipt 仅证明修复行为；fresh ordinary validation 才能提供原义务的当前证明。保留 failed evidence 及原预算。
- 同一 binding 修复、prospective repair、历史 source-change 用途和前驱重验分别沿已有合同消费；验证退休不会遗留已消费 repair directive，也不会过早抹去未结算 authority。
- 原 CWI 真实满足后再推进后继；终态仍 all-of 核验所有原 Goal/DoD/交付义务与资源适用性。

退出要求：一条生产 owner/scripted-provider 主链真实经过“输入一致 → 行为失败 → 精确实现修复 → fresh 验收 → 后继 CWI → 正式交付”，并在关键 CAS/receipt/交付回复丢失处恢复，不重发已完成 effect、不刷新预算。

## 6. 建议实施与验证批次

1. **主体批次：R1 + R4。** 完成默认声明、精确 availability、普通多轮与最终消费者组合。已有公开十分钟 fullflow 必须真实通过；先用真实 owner + scripted provider，无收费。
2. **输入批次：R2。** 先确认版本化修订合同，再实现新生成/复用/修订的完整边界。旧弱输入和新输入两条路线都验证，不能删除旧文件凑 fresh 正例。
3. **闭环批次：R3。** 将真实失败、实现修复、fresh proof、后继义务与最终交付串入同一公开入口链；关键切点恢复和 stale/duplicate/unknown/预算门禁完成。
4. **启动与成本：R6、R5。** 分别完成精确准备回执消费及缓存身份/网关事实核对，不增加无关 UI 或通用平台功能。
5. **部署 live。** 先记录最终源码/console/产物身份，再部署。支持的第二种任务或中立 fixture 加上内容完全不同的多 Workspace 并发，核对 authority、scope、输入、预算、provider 会话、缓存身份与交付隔离；不声称未支持的 Profile 已通过。

R1 的既有 fullflow 与 R2 的新增修订场景是互补验证，不需要为跑既有主链先强行制造输入冲突。最终组合场景再证明它们能够协作。

live 前置要求是无收费公开主链真实可达与通过，不是单元测试数量够多。之后有限真实模型验证应按内部账本核对每一步：原义务 → 受权工作 → 独立审查 → 实际验收 → 必要修复 → 后继 → 全部原义务及交付。每到失败点先保存归属，避免靠连续收费 Restart 碰成功。

新 Profile/work policy 改变 startup seal，不能热替换当前 Workspace。使用支持的显式修订流程重新六审与人工精确确认；若没有修订入口，则新建 Workspace。当前两个 failed Run、旧输入及原始诊断保留，新版本不能自动复活它们。完整 STEP05 未完成前，相应启动边界仍不得宣称收口。
