配置公开安全投影为 defaultChat `ai-proxy/gpt-6.1-sol`、`restartRequired=true`；三次实际调用均为 `deepseek-flash`。因此本轮不能记为 GPT 模型验证。需要使目标配置在运行进程中生效，并在下一次新事务开始前核对实际 owner 目标及随后审计。本轮没有改配置或重启现有服务。

### 2. 首次审查未通过精确身份校验

审查应绑定的候选 hash 为：

`goal-specification-sha256:8c926c32fea53aa911e9ba1d4d459ed993db647e1c0a1b09b7a8f28a4f3a7af7`

返回值在 `...c32fe` 后漏一个 `a`，hex 从 64 位变为 63 位。`ParseReview` 在 `internal/modules/application/workorchd/biz/appservice/specifications/proposal.go` 拒绝身份不相等的响应，符合预期；原 JSON 中虽有 FAIL 字段，仍不能计为有效 FAIL 审查。其语义反馈只作排查材料。

后续必须保留原失败，按明确的新输入或新请求合同开展下一轮；不得替换原 hash、改写响应、把本条提升为有效审查，或反复重放已失败 permit 期待自动重试。

### 3. 候选尚不能证明完整验收覆盖

原 PRD 有 42 个勾选验收条目。候选完整保留规范化 Goal，形成 3 个维度、3 个需求分组、29 项义务（13 项模板 + 16 项补充）及 29 项验证声明；其中 **24 DECLARED、5 UNVERIFIED**。条目数量本身不能证明覆盖充分。

五项 UNVERIFIED 对应模板中的需求提取与计划映射、owner state_change、Git 快照、结果摘要、逐项 evidenceRefs/交付索引。候选声称当前 dodItem 能力不能承担这些用途；这是模型声明，尚未独立证明 Profile 合同确实缺失。应逐项核对 owner/Profile 已声明能力及实际消费者，再修正声明或必要合同，保留原义务。

独立阅读也确认当前义务主体是通用模板及补充边界；健康、核心转发、provider/fallback、CSV、归档、监控等原验收主项尚未建立清晰逐项承接。原 Goal 全文并未丢失，但保留全文不能替代结构覆盖与有效六审。应在下一轮候选中核对原 42 项承接，不能以删除难项或放宽 required 获得通过。

### 4. 生产 Web 诊断元数据/原文边界接线错误

全页刷新、重开规格后，页面先提示“已保存的解析错误缺少原文”；点击按需读取后又提示“诊断元数据与失败记录不匹配”。

最小修复方向：列表只验证元数据自洽性；按需读取后先匹配 workspace/permit/phase/failure 及全部 hash/bytes/观测元数据，再对真实原文做 byte/hash 校验。不得将原文重新混入普通列表，也不得取消完整性或迟到响应校验。应增加与真实 metadata-only DTO 一致的组件回归，随后用已有原诊断复验，无需为这个展示问题新增收费调用。本轮只定位和记录，未改生产代码。
