### 阻塞一：MCP 连接消费者未接通

实际选中模板默认 `mcp-lsp-bridge`，9个能力：definition、diagnostics、hover、initialize、references、repair、shutdown、status、sync。没有 selectionFailureCode，registry 前后完全相等。stdio 命令 `lsp-bridge`，环境声明绑定托管配置和工作目录；本机能够找到 lsp-bridge、gopls 和 skill-hub，不能诊断为命令缺失。

`internal/modules/kernel/workspace/pkg/models/preparation_mcp_selection_evaluation.go` 对成功非空选择固定返回 connection_pending；`workspace/readme.md` 的准备协议明确 registry/selection 不连接、不 initialize、不提供连接 epoch/currentness。原检查确实没有产生连接证明。这是生产准备能力缺口，不能通过删除默认 MCP、手动执行 CLI 或把 registry 一致当成连接成功解决。

后续收口应由 MCP 能力 owner 提供精确选中声明、托管路径、连接结果及生命周期/有效性事实，经 typed 合同交给准备消费者裁决；显式接纳、预算、原操作恢复、失败/未知及 stale 仍须保持。不能在只读 GET 或普通重放中偷偷连接，也不能将连接检查升级为业务工具调用。

### 阻塞二：完整 bootstrap 超过封存焦点上限

显式检查及原请求重放/恢复都返回 `bootstrap_structure_rejected`。该失败独立于 9/10 checklist，不能只报告 MCP。

用 `/tmp` 内 Go overlay 定向测试，使用正式 file repository 解码，再经过生产 `PreparationCompilationSource.Model()`，只对原归档调用 `CompileOriginalPreparedBootstrap`，得到完整私有诊断：

```text
runtime coverage focus compiler produced 70 focuses, exceeding sealed policy limit 64; configure bounded acceptance slices
```

诊断122 bytes，SHA256 `a3aaf32b051af31617e5631982123c1b6e275f4495d1ab9f04f01227b42f29bb`。纯复现通过，耗时约3秒，前后 owner 哈希一致；无 owner 写入、配置/环境替换、外部操作或 Run 初始化。

源码 `activationcore/runtime_focus_compiler.go` 为每条工作项生成一个 focus，最终按封存的 MaxFocuses 检查总数。本候选67条 DoD 加其他必需来源形成70个焦点，封存策略上限64。单纯调整 acceptance slice 的每组条数不会减少焦点总数，不能按错误提示直接改分组声称解决，也不能删除原准则或运行时擅自抬高已封存上限。

后续应先确定有界容量方案，并把精确候选到 bootstrap 的可编译性检查前移，防止六审及 eligible 后才发现结构容量冲突。若方案改变模板/策略或规格，须经正常新候选审阅确认，保留当前精确合同与失败历史；本轮不改已封存对象。尚未证明该项和 MCP 修复后即可通过整个 STEP04。
