## 已落地内容

1. 新 authoring 事务封存 `workorch.authoring.owner-bound/v2` 与阶段 schema hash。派生只返回 AdditionalItems；提案只返回语义 mapping；六审只返回结论、原因与原引用。input/template/resource、review kind/proposal 等机器身份由 owner 根据原 permit 构造独立 typed 结果。原 provider document/wire 不补字段、不改写。
2. 所选版本进入原请求及 permit；完成、重放、重新读取、确认和历史恢复按原版本解释。空 wire 身份仍是原 v1；未知版本、混用形状、漂移和冲突阻断，不为旧失败／已消费 permit 增发许可。六审与用户确认仍必需。
3. v2 成功派生、提案、审查保存独立原文字节与 byte count/SHA256，owner 完整重开时重解码比对 typed 结果。普通 DTO 只有 metadata；受限 success-byte-audit 查询可读取这些原文，按 Workspace/permit 限定，重复读取不写入、不调用 provider。私有准备编译显式保留完整原文，不能把 metadata 当完整归档。
4. 默认软件模板增加 `workorch.template-source-proof/v1`：精确模板 ref＋原文映射到确认后 DoD ID，不硬编码受用户条目数影响的 dod-NNN。模板第 3／4／13 条分别绑定真实 File 变更回执、最终 Git snapshot、正式 Result evidence index；声明选项提供实际合并后的 consumer、版本和消费阶段。所有路径使用同一纯编译器，activation 核对封存 Profile hash。
5. 普通 validation 与 typed guard 保持 AND。终态消费者仅在 `post_terminal_delivery` 消费；普通 DoD 验证不等待尚未产生的最终 Git／Result。新增 `runtime/terminal-receipt-choice/v1` 只为终态 receipt 提供 2–4 个 exact kind/variant 的 OR：默认允许 file/write 及 patch/apply 的 file_write、text_replace、unified_diff。owner、effect、来源和原 receipt 栅栏仍全部核对。
6. raw Profile 与持久 JSON 均拒绝超额 alternatives，避免 Go 固定数组静默丢元素；未知字段、重复／空洞、未知 variant、错 owner／effect／phase 等继续阻断。零值新字段不改变原规则 JSON/hash。
7. 原始来源缺失的正式行不能由模板顺序／相同文字猜出模板来源；通用准入使用实际 inventory。独立 Profile 的合成 formal-row 测试与真实 authoring/default-template 测试明确分开。
8. 登记前一版本 software-dev 精确内容指纹及冻结 fixture，维持既有显式升级流程。现有模板不会因启动而自动覆盖；定制内容、旧 Workspace 封存和旧失败记录保持原样。

Runtime 影响限于 SM-4 终态 receipt 选择及 shared typed rule 的严格恢复解码；SM-1 生命周期、SM-2 reducer／普通验证门禁、SM-3 dispatch 权限与运行预算未新增转移或放宽。Template/Profile 编译仍是纯数据处理，资源 owner I/O 仍走 concrete typed EventHub。
