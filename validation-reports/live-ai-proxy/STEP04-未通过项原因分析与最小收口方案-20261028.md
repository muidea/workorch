## 1. SkillHub 首次登记的生产者输出合同

### 原因链

- Workorch `contextregistryports/skillhub_preparation.go` 用 `skill-hub status --json`，project cwd 为原交付目录，stdin 未设置，子进程读取到 EOF。
- SkillHub `internal/clis/skill-hub/status.go:96` 先尝试已配置服务，不能取得成功结果时进入本地 `RequireInitAndWorkspace`，然后才输出 status JSON。`--json` 没有传入前置项目登记交互。
- `dependencies.go:201` 的 `EnsureProjectWorkspace` 在未登记时向 stdout 输出提示；读取输入的错误被忽略，EOF 与用户空回车都归为空字符串，走默认创建分支。
- 创建进度也写入 stdout。最终虽 exit 0，stdout 仍是“提示＋登记进度＋JSON”。Workorch 对完整文档判为 `invalid_status`，没有清洗或截取原输出，这是正确拒绝。
- `.agents/skills` 目录存在与 SkillHub state 中已登记是不同事实。项目 items 为空也不等于全局／Registry Skill 不需要参与选择。

### 独立隔离复现

本轮实际执行本机已安装 CLI 一次，设置独立 `SKILL_HUB_HOME`、显式关闭 service bridge、空项目登记表和已存在 `.agents/skills`，stdin 为 DEVNULL。未使用生产 SkillHub state 或项目：

- exit 0；stdout 529 bytes；stderr 0。
- 完整 stdout 不能解析成 JSON。
- 独立登记表中真实新增了该项目。
- stdout SHA256：`ad119d97e85b591f98cd855b09bb45b92c1da51c2b76e436ccee7a56d3f0d90a`。

生产 760 bytes 与本轮 529 bytes 不应直接比较；路径不同导致输出长度不同。两者支持同一首次登记原因链。源码解释与实测行为相符，不据此声称已建立外部二进制的源码 attestation。

### 最小改动

优先在 SkillHub 生产者修正 JSON 模式：stdout 始终仅输出一个完整 JSON 文档，提示和进度进入 stderr；机器调用不得依赖 EOF 被当作用户同意。首次登记行为应有明确的非交互约定，保留用户已经接受的服务访问及状态保存效果，不改造成新的严格只读产品。

如需要显式登记选项，必须先在 SkillHub 实现及验证，再由 Workorch 适配器传入；不能向旧 CLI 猜传不存在的 flag。应覆盖本地和服务模式，不静默关闭生产 service bridge。Workorch 保持整文档校验与原始双流保存，不增加“寻找最后一个 `{`”或日志剥离兼容器。

现有 `TestPreparationSkillHubExecUsesCurrentArgumentsAndPreservesStatusEffects` 是 shell fixture；实际二进制的 `TestPreparationSkillHubInstalledBinaryProjectStatusEffects` 预先写入了项目登记。因此它们没有覆盖这次“目录存在但尚未登记”的首次路径，必须新增此真实 CLI 用例。

## 2. 当前数据需要独立的精确对账出口

`PreparationSkillHubStatusFacts.EffectsUnresolved()` 将已派发且带 FailureCode 的记录保留为 unresolved。当前 project 的解析失败因此也阻止后续新请求。

`beginWorkspacePreparation` 对 blocked/failed 原请求的普通重放和 recover 均只读回原结果；对任意 reserved/unresolved 历史拒绝新身份。Web 也据此禁用新检查／初始化，而 blocked 原请求不进入 pending 恢复按钮。这是现行合同的真实结果，不是仅改按钮即可修复的前端缺陷。SkillHub 修复或项目现在已登记，都不会消除旧门禁。

建议单独增加 owner 管理的显式对账结算，而非改写 v1 历史：

1. 请求只引用精确 Workspace、原 request、原 effect 引用及当前 Workspace revision；完整旧内容和摘要由服务端真实读取，调用者不能提交 PASS、scope、目录或替代 stdout。
2. Workspace owner 验证原操作已经完成、本地 dispatch 不在途、原回执与来源绑定，保存追加的对账事实。原失败、退出事实、完整原输出及原 content hash 保持不变。
3. 必须区分“本地进程已结束、解析失败已知”和“可能存在外部未决保存”。CLI 会优先访问服务且失败后可 fallback，不能仅凭 exit 0／流完整推断服务端绝无在途效果；已有登记也不能反证没有在途写入。需要可核验的结束／对账依据；没有依据时仍阻塞，不能仅加 `force=true`。
4. 对账结论只允许解除对应旧效果的后续请求栅栏，不给旧检查补安装材料或通过分，不重新派发 status、不授 ready/M3。随后使用当前 revision 接受新的显式检查，重新取得完整当前来源。
5. 幂等重放、响应丢失、CAS 冲突、进程重启、错误 effect、跨 Workspace、漂移及未知外部效果都必须有定向覆盖。GET 和现有 recover 保持原只读／不重派发语义。

此项需要明确新的结算合同；不能直接把 `EffectsUnresolved()` 中的 FailureCode 判断删除，也不能用空库存绕过。具体外部效果对账依据在实现前仍需选定，不宣称当前已有足够正例证据。

## 3. Skill 与 MCP 按依赖顺序验证

`CompilePreparationSkillSelection` 要求 Registry、Soul、同请求 SkillHub global/project 安装材料完整且绑定一致，然后按原 Goal/DoD 和执行 Soul allowlist 做组合选择。

`CompilePreparationMCPSelection` 在 Skill 选择存在失败时即返回 `skill_source_incomplete`，之后才组合 Skill 声明的 server/capability refs 与 Workspace 显式默认项。因此本轮没有足够证据要求修改 MCP 连接实现。

验收应先证明新请求的两个 status 整流可解析、安装指令及必要辅助文件观察完整、选中 Skill 来源与 allowlist 一致，再观察 MCP 的真实选择和 required connection 结果。global 的 10 个 reference 不是最终选中 10 个 Skill。项目空集合也不能跳过全局来源或强行将 MCP 记为 N/A。

## 4. Provider：缓存与配置授权分开收口

`CatalogService` 的目录缓存在进程内。`catalog_cache_observation.go` 只查看缓存，不发网络、不等待刷新、不淘汰；新进程的 miss 并不等于 API key 无效或模型下线。

最小运行准备是通过既有配置界面显式刷新目录，随后在有效期内执行新准备检查；准备 GET／检查不隐式发起外部 probe。即便目录和容量完整，当前 `PreparationProviderSelectionCompilation.BlockedReason()` 仍固定返回 `provider_selection_budget_observed_authorization_pending`，没有授权通过消费者。

进一步核对 AetherRelay 源码发现可复用来源，而非必然新增接口：

- Proxy handler 校验客户端 key，再将真实 `ClientIdentity` 放入 context。
- `handleModels` 使用该 identity 的 `ProviderAccess` 编译 `/v1/models`。
- `buildModelsListResponse`、`modelSupportedEndpoints` 仅使用该 policy 允许的模型候选，过滤模型、端点及容量来源。
- `TestModelsAreScopedToAuthorizedProviders` 覆盖无权 provider 不能贡献模型、端点、容量及转换能力。

因此可以提出 AetherRelay 专用的版本化适配器消费合同：将同一受信配置连接／凭据身份下、未过期且完整的已认证目录结果用于证明“该时点配置权限允许精确模型和所需端点”，保留原 raw 来源、观察时间、owner epoch 与精确目标绑定；凭据变更、缺模型／端点、401/403 或过期均阻塞。不能把此语义默认赋给所有 OpenAI 兼容网关，也不能单靠 caller 提供的 catalog 宣称授权。

此证据不证明未来持续权限、剩余额度、上游账号当时可用或实际推理成功；AetherRelay 明确将请求时健康／熔断应用在后续路由阶段。若本步要求这些更强事实，仍需对应真实证明。当前部署是否与所查 AetherRelay 源码版本一致也需确认，不能仅凭 baseURL 和 key 宣称该消费者已经接通。此轮未访问网关或使用凭据。
