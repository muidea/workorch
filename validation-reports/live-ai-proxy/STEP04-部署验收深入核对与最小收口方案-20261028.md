## 一、结论及范围

SkillHub v0.13.7 的新登记、原回执查询恢复主体已有有效的实际进程正例，不需要重写。当前应优先同步标准验收工具、绑定正式构建身份，并验证真实业务资源选择；不要再把旧 Workspace 的历史补偿作为主体推进前提。

上一份报告的四项剩余事项需要进一步拆分：

| 项目 | 深入核对结论 | 收口类别 |
| --- | --- | --- |
| 旧 status unresolved | 已完成失败观察，没有原 status 回执/释放合同；升级和原 recover 均不能解锁 | 历史数据路径选择，非新登记接线缺陷 |
| Provider cache miss | 仅第一道阻塞；fresh catalog＋容量编译后仍固定 authorization_pending | 缓存操作条件＋后续授权消费合同 |
| 标准 verifier | status-only fixture 拒绝新 register/query，初始化投影和 revision 仍为旧 v1 | 本轮明确的测试工具缺口 |
| 构建身份 | 证据绑定实际产物 SHA，但不能证明全体构建输入与当前提交等价 | 构建/部署证据链 |
| 真实资源及最终正向结算 | 隔离只验证空 Skill/MCP 选择；当前操作账本也不能表示整体 ready/M3 | 完整 STEP04 仍需明确的功能后续 |

目标应分别记录为：①新初始化/恢复主体通过；②真实业务除 Provider 外的所有 required 项通过；③完整 STEP04 准备正例通过。不能把①等同于②或③。STEP05 的 Start/Restart 回执消费、Runtime 执行仍不在本方案内。

## 三、旧 status 为何不能通过现有恢复解除

精确路径：

- `models/preparation_skillhub_effects.go:97`：命令已开始且有 FailureCode、未知退出、不为零退出或不完整输出，均归为 effects unresolved。
- 同文件 `Summary()` 与持久迁移校验：完成后的效果材料不可改写；新历史只能在之前所有效果均 recorded 时追加。
- `biz/activation_preparation_internal_event.go:68`：已有 blocked/failed 原请求，recover 仅返回历史；不会重新执行外部观察。
- 同文件 `:86`：reserved/unresolved 存在时，新 check 拒绝。初始化也不能用新登记越过该旧 fence。

实际归档有两个不同历史效果：第一次 project catalog 尚不存在，命令根本未启动；第二次 project 命令确已退出 0、stdout/stderr 完整，但 stdout 解析失败，保存 `invalid_status`，其字节数为 760。后者不是“进程还在执行”的证据，也不是已取得可消费库存或外部副作用结算证明。当前合同有意把失败观察与效果未决同时保留。

因此三种做法均不成立：重放旧初始化以追加新登记；对旧 blocked 请求 recover 期待重取 status；删旧 failure 或改成 recorded 以放开新请求。v0.13.7 的 registration query 只认识登记请求，不能查询旧无 request-id 的 status。

**推荐本轮不实现历史兼容迁移。** 用户此前已明确首版不考虑历史兼容性；保留旧 Workspace/诊断，在新的 Workspace 通过正常创作、独立审查、人工精确确认，再执行 v2 初始化及新检查。沿用相同 PRD 原文，不能把旧 candidate/eligible 手工复制到新 owner，不清空全局 SkillHub 状态，不批量删除旧数据。新的业务 Workspace 创建/确认在正式 live 时显式执行，本轮没有执行。

若后续明确要求救回原 Workspace，才单独设计版本化的旧效果对账/封存合同：至少绑定原 Workspace/request/effect/ref/目录/Hub 身份与原始材料，提供可信的完成/不再迟到事实，追加独立结算账本并经 Workspace 私有 reducer/CAS；不覆盖历史，不授库存 credit，新检查另取当前证据。当前输入不足以实现这条路线，不能把“退出 0”或人工口头确认直接当作副作用清零。

## 五、真实业务资源验证：不能直接承诺新 Workspace 只剩 Provider

前次隔离正例把 Hub home 和 Codex/Claude/OpenCode skill 目录都隔离为空；测试 Soul 也明确不选择库存项。生产旧 global 原观察则包含 **4 个唯一 Skill、8 条安装项、2 个 agent**。这不说明生产必定会选择它们，但足以证明两种环境并不等价。

`models/preparation_empty_selection.go` 只对独立重编译后精确为空的 Skill/MCP 选择授单项通过。`preparation_mcp_selection_evaluation.go` 明确将非空选择保留为 `mcp_selection_compiled_connection_pending`。因此不能根据隔离 10/11 保证生产新业务必然 9/10。

最小推进方式：

1. 在新业务 Workspace 使用实际 Template/Soul/全局库存和真实 MCP 配置，先完整编译选择结果；不通过清空库存、换成测试 Soul 或改 DoD 来制造空选择。
2. 若实际选择为空，复用已实现的精确空集合消费者即可，不新增机制。
3. 若实际选择非空，仅对确实被选中的 Skill/MCP 补当前性/连接事实消费者：资源 owner 提供精确目标、版本、实际观察结果和期限；Workspace 按原选择及当前绑定裁决。不存在的 owner 观察合同先审阅，不把注册表存在或结构编译成功当作连接通过。
4. 保持 STEP04 的操作限制：不自动安装/同步技能、不执行 MCP 工具、不引入收费模型。需要实际连接握手时，先核对它属于已允许的准备观察，并定义精确预算及副作用边界。

退出条件：真实生产资源路径下，除 Provider 外所有 required 项实际通过；非空且未取得真实证明时准确 blocked，不扩大声称范围。生产浏览器还需覆盖新初始化/原请求恢复/显式检查正例；前次浏览器仅覆盖旧 fence 禁用态。

## 六、Provider 历史分析与已撤回建议

本节下述“两层前置门禁”建议已被用户本轮纠正取代，保留用于说明偏差来源，不再要求实施。
正确收口是消费 Workorch 已配置的 LLM 默认项／Workspace 显式偏好，启动时封入运行上下文；
准备检查不以 catalog 热缓存或独立授权回执为前提，实际调用仍执行原 Runtime 校验。

**第一层：目录缓存。** LLM `CatalogService` 的 entries 在进程内创建，重启后为空；`observeCache()` 明确禁止外部 HTTP、刷新、等待在途刷新或回退。故本次 cold cache 的 `provider_cache_miss` 符合现行合同，不证明 API key 错、模型不存在或网关不可达。

收口先复用现有系统配置的显式 models refresh：在允许外部目录请求的单独动作中由 LLM owner 取回完整目录；在 TTL 内执行新的准备检查。准备 GET/recover 不负责预热，也不把旧 blocked 记录重新计算为成功。若继续坚持本轮零外发，可用本地 fixture 验证这条机械链，但生产该项必须保留 blocked。

**第二层：授权证明消费。** `preparation_provider_selection.go:23` 在 selection 编译成功时仍返回 `provider_selection_authorization_pending` 或 `provider_selection_budget_observed_authorization_pending`；目录和容量预览齐全也没有 PASS 分支。

下一步应先核对网关现有合同能否对当前凭据、精确模型及操作给出可靠权限事实，不预设必须新增接口。仅有 baseURL/API key、模型列表可见或创作期调用成功，均不能直接替代当前目标的准备授权合同。若现有接口不具备该语义，再提出窄的版本化只读合同，至少包含可信签发来源、凭据作用域的非敏感身份、精确 model/operation、allow/deny/unknown、签发/到期及撤销或 revision 语义。

由 LLM owner 验证外部回执并输出 typed、可独立反查的观察；Workspace 保存原事实并消费。公共 Web 只输出有限状态/原因，不传 key、原始权限正文或 caller PASS。不做后台 probe，不用放宽授权替代功能实现；收费推理探测属于另行选择的验证路线，本方案不默认采用。

退出条件：精确目标的能力、容量和可信权限 all-of 满足后才允许该单项通过；缺失/过期/错模型/错操作/配置漂移均阻塞。恢复不刷新、不调用 provider，进程重启不能自动把旧观察当当前。

## 七、构建身份：补过程证据，不补造历史

现有 `build_identity.py` 和 STEP01 `build_candidate()` 已提供构建前 capture→真实 console/Go build→produce→独立 verify 链路；不需要另造一套身份工具。

最小方案：在最终代码冻结后完成源码和资产快照，用受控构建生成全新二进制、命令日志及 manifest；将该二进制用于隔离复验，然后部署同一 bytes。部署后读取实际运行 executable 的 SHA256、buildinfo 并核对 manifest，浏览器资产另做字节比较。提交号、buildInput、consoleTree 与 binary 四种身份分别保留。

上次 deployed SHA 的结果继续作为该产物事实，不倒填 capture，不把当前 git HEAD 补写为其构建身份。用户负责部署时，应交付精确产物/manifest 与验证命令，部署后核对实际 bytes，而非只询问“是否已部署最新”。

退出条件：正式验收可反查最终源码输入、嵌入资产、构建二进制和实际运行进程的同一身份链；dirty build 若保留完整输入身份可以如实记录，不以 clean 标签代替内容绑定。

## 八、完整 STEP04 的正向结算须单列

`models/activation_preparation.go:16` 明确当前 v2 是 accepted→blocked 的阶段性账本，不能表示整体 positive readiness/M3。实际 reducer 在 `activation_preparation_internal_event.go:519` 固定结算 blocked。all-of assessment 的 `checks_passed` 也不是准备完成凭据。

因此“解决 Provider 即完成第四步”不成立。若退出目标是完整 STEP04，仍需按已批准 no-Run 顺序和现行资源合同补：所有 required 原事实合取→同一结算窗口独立核验当前性→Workspace 精确 final CAS→持久历史完成身份/材料与当前有效性分轴投影。旧 blocked 不在 GET 中升级，fresh intent 的 reservation/epoch 竞争必须使当前性失效；重启保留历史完成事实，重新观察前不声称当前有效。

这里必须同步 Workspace models/reducer/repository、typed events、HTTP/Web 与并发/重启反例；不能只改页面文案或将 blocked 枚举替换为 ready。若为此调整 Runtime/fresh intent 既有行为，实施前另读 Runtime 阶段合同并明确所影响的 SM，不能把本方案当成扩大执行授权。STEP05 消费准备回执及执行派发仍单独验收。

## 九、实施顺序与停止条件

1. **先修标准 verifier**，让新登记/恢复主体有稳定、可重复的标准验收入口；按本轮纠正验证配置检查通过，同时保留旧历史与配置无效反例。
2. **生成并绑定正式产物**，执行标准无收费 HTTP/真实进程重启回归；交付可核验部署身份。
3. **用新业务 Workspace 做真实资源链验证**，保留旧历史；先完成除 Provider 外的业务路径和生产 Web 正例。按真实选择决定是否补非空消费者，不提前建设无关机制。
4. **纠正 Provider 配置消费**，自动读取 Workorch 已配置目标，避免引入独立网关授权前提。
5. **目标若为完整 STEP04，再完成正向结算/M3 退出验收**；只有 required、当前性和 final CAS 全部通过，才能关闭第四步。否则准确交付“除 Provider 外主体通过”及明确未实现项。

本轮未实现上述改动、未解除任何旧 fence、未创建新业务 Workspace；核对结论与实施完成严格分开。
