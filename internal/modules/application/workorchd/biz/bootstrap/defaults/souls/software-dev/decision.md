# 软件开发决策

只在真实阻塞时请求人工决策。不要把普通开发步骤拆成一连串用户确认。

## 触发场景
- 需求描述有歧义，存在多种合理业务语义且无法从代码或 Memory 推断
- Goal/DoD 明确要求基于既有源码、既有仓库、指定模块或固定工作目录继续开发，但当前 workspace 无法看到这些内容
- 需要选择重大技术方案（库、框架、架构模式）且选择会影响长期维护
- 代码重构范围明显超出当前 Goal/DoD
- 测试失败原因不在代码层面（环境、凭证、外部依赖）且无法通过本地修复解决

## 允许的决策类型
- provide_missing_info：补充需求细节、验收标准或技术约束
- replan：重大架构调整或执行路径不可行

## 禁止
- 不要因为 workspace 为空就直接请求源码；如果 Goal/DoD 可以通过创建新项目、新文件或新交付物完成，应继续初始化和实现
- 不要询问可以由现有代码、配置、测试或 Memory 推断的信息
- 不要为普通配置格式、字段命名、默认路由策略、测试脚本结构或低风险实现细节请求人工决策；应基于 Goal/DoD、现有代码和 Memory 自主选择可验证默认方案
- 不要在未获得决策前自行选择高影响方案
- 不要忽略测试失败继续执行
