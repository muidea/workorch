# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Also used as `AGENTS.md` (multi-agent shared guidelines). Prefer editing this file once; keep `CLAUDE.md` as a symlink to it.

## Project Structure & Module Organization

WorkOrch is a Go service (`github.com/muidea/workorch`, Go 1.26.x) with an embedded Web console and TUI-first CLI. Single `go.mod`; “multi-module” means directory/ownership boundaries, not multiple Go modules.

| Path | Role |
| --- | --- |
| `application/workorch` | Binary entry. Default mode starts TUI; `--server` starts HTTP/Web |
| `internal/services/workorch` | Process-level wiring: local/remote backend, CLI, TUI, agent session |
| `internal/initiators/workorchruntime` | Repository provider/factory only; no EventHub, runtime-policy, or bootstrap export |
| `internal/modules/application/workorchd` | Server app module (`biz`/`service`/`pkg`): typed bootstrap, HTTP/SSE/projection — **does not** own Runtime drive |
| `internal/modules/kernel/{orchestrator,governance,system,workspace}` | Multi-owner coordination Modules: Runtime convergence, governance, startup defaults and Workspace coordination |
| `internal/modules/blocks/*` | Resource owners (`run`, `result`, `decision`, `approval`, `memory`, `skill`, `soul`, `mcpregistry`, `eventstream`) and capability blocks (`llm`, `file`, `git`, `shell`, `ssh`, `web`, `mcp`) |
| `internal/pkg/workorchruntimecontract` | Typed Runtime contracts (implementation SoT with orchestrator `readme.md`) |
| `web/workorch-console` | React/TypeScript/Vite/Ant Design console source |
| `web/consoleassets` | Embedded production console assets (generated by build) |
| `docs/` | Local design, plans, reviews and validation records; excluded from Git. Navigation: `docs/README.md` |
| `config/`, `config/file/` | Default / file-backed TOML configs |

Module/Block shape: `module.go` / `plugin.go`, `biz/` (orchestrator has `biz/runtime/`), optional protocol-adapter `service/`, `pkg/`, `readme.md` (component interaction SoT). Owner units do not expose direct service facades. The 22-unit type baseline is 1 Initiator, 5 Modules, and 16 Blocks; directory placement follows that classification.

### Runtime ownership (production path only)

> Application builds typed `RuntimeBootstrap` and issues Start/Resume only. Run owner CAS-persists the Runtime aggregate. Orchestrator is the sole reducer / drive / evidence / governance-resolution authority. Capability blocks execute typed ops and return results. Result stores already-judged outcomes. Eventstream / projections are audit/display only. Recovery = idempotent re-drive from aggregate.

- Cross-owner I/O: EventHub + concrete typed command/result only (no cross-owner service/repo, no `map[string]any` into authority).
- Forbidden production surfaces: StagePacket, NextAction, DispatchNextStep, ExecutionContextPatch, auto replan successor, and map-based authority rebuild.
- Workspace owner first persists a pre-seal `DefinitionAdmissionCandidate`; pure admission accepts complete `all_of` semantics
  only. Unsupported one-of/ambiguity opens a blocking clarification ticket and cannot create a Run. Promotion seals Goal/DoD,
  template/profile policy snapshot, resolved project directory and `StartupInputHash`; all Start/Restart ingresses require an
  eligible `WorkspaceActivationAdmission`.
- A bounded SM-3 semantic-plan document may propose per-CWI proof after startup input is sealed; capability owners return
  feasibility; only an SM-2 private internal event may seal `CoverageEvidenceBinding` and the reconciliation contract before
  operation candidate/dispatch. Runtime LLM processing may not modify the sealed startup input.
- Normal Web workspace setup takes template, Goal, resource references and optional user acceptance requirements; DoD is
  derived, independently reviewed and materialized only after exact user confirmation. TUI has no authoring wizard and must
  reject retired direct definition writes. Creation/confirmation never starts a Run; execution is an explicit separate intent.
  Setup must produce a resolved workspace directory, but the directory input is optional: blank input resolves to
  `.workorch-workspaces/<workspace-id>`. It must not require raw
  `contextHints`/`evidencePolicies`, target, recipe, check, metric or artifact JSON from the user.

### 文档存放与 Git 基础规范

- 后续所有设计和验证相关文档统一放在 `docs/`，包括现行规范、候选设计、实施计划、评审、收口记录、验收报告及证据索引。
  现行规范沿用上述主题目录；计划使用 `docs/plans/`，验证报告和证据索引使用 `docs/validation-reports/`。
  不再在项目根目录新增或维护 `plans/`、`validation-reports/` 等独立文档目录。
- `docs/` 为本地维护目录，整个目录不纳入 Git 提交。`.gitignore` 必须包含根路径 `/docs/`；已有受控文件应仅取消
  Git 跟踪、保留本地原件。不得使用 `git add -f` 或其它方式将其重新纳入提交。提交前核对 `git ls-files -- docs` 为空。
- 文档集中存放不改变权威层级：候选设计、计划、评审和验证记录必须与现行规范分开标识，不因放入 `docs/` 就成为设计权威。
  源码及其现有组件合同入口继续按 owner 边界核对；新的独立设计说明统一写入 `docs/`。
- 构建、自动测试和 CI 不得依赖本地 `docs/` 存在；可执行合同和必要测试数据随代码维护，不能用跳过行为门禁替代。
- 本规则优先于此前“docs 仅维护现行规范”或“validation-reports 可提交”的旧存放约定。历史文档迁移须保留内容并核对引用，
  不恢复或覆盖用户已删除的历史文件，不删除受限原始证据。

LLM request / cache / budget: also read `docs/00-core/runtime-request-cache-note.md`.

## Build, Test, and Development Commands

```bash
make deps              # go mod download + console npm ci
make build             # console assets + ./bin/workorch
make run               # HTTP service with config/
make run-file          # wipe .workorch-data, file-backed config/file
make fmt / make fmt-check
make vet
make test              # go test ./...
make test-race
make ci                # local CI baseline (fmt-check + vet + test + build)
make release-check     # fmt-check + vet + test + verify-boundary-contract
make console-build     # web/workorch-console → embedded assets
make verify-boundary-contract   # runtime/Web business neutrality
make verify-ci-mvp-file         # CI-safe deployed checks (mock providers)
```

Targeted Go tests (prefer before full suite):

```bash
go test ./internal/modules/kernel/orchestrator/... -count=1
go test ./path/to/pkg -run TestName -count=1
```

Web console local dev:

```bash
cd web/workorch-console && npm run dev    # after make console-deps / make deps
```

TUI (default binary mode, no `--server`):

```bash
go run ./application/workorch -config-dir config
# or after build: ./bin/workorch -config-dir config
```

Do not commit generated runtime data: `.workorch-data`, `.workorch-workspaces`, `bin/`, `node_modules/`.

## Coding Style & Naming Conventions

- Go: `gofmt`; short lowercase package names; prefer existing module boundaries and helper APIs.
- Web: TypeScript, React, Vite, Ant Design under `web/workorch-console/src`.
- Commits: concise imperative summaries (`fix runtime incremental artifact convergence`, `docs: reorganize workorch documentation structure`); keep scoped. PRs: behavior change, verification commands, config/migration impact, UI screenshots when relevant.

## 数据保真原则

- 业务输入、provider 输出及诊断材料必须保持原样；禁止为脱敏而替换、清洗或改写内容，禁止用摘要替代原始数据或静默截断，避免跨层传递产生偏差。
- 协议必需的编码转换必须可逆。原始文档按 bytes 保全，使用字节数和 SHA256 校验存储、读取及展示链路；显式合同规定的规格规范化不得覆盖原始诊断材料。
- 超出明确的存储或传输边界时，必须显式报告未保存/未传递及原因，不能将部分内容标为完整，也不能因此把已知失败重新标为结果未决。
- 原始诊断通过 owner 管理的受限运行存储和读取边界保护，不通过改写数据保护。不得将原始诊断、凭据或 live 配置提交到 Git，也不得把无关配置密钥混入诊断或通用日志。
- 诊断仅用于排查，不是规格、准入或执行权威；不得为保留原文而绕过严格校验、owner 边界、预算或人工确认。
- Web 不得使用 localStorage、sessionStorage、IndexedDB、cookie 或其他浏览器持久机制保存业务输入、事务恢复身份或服务端数据。交互数据仅暂存在页面内存；已保存数据与恢复依据由服务端 owner 管理。未保存输入在关闭／刷新后丢失，界面必须明确说明，不能通过浏览器缓存恢复旧事务。

## Testing Guidelines

- Focused `*_test.go` beside changed code.
- Runtime, LLM request assembly, event projection, TUI, and presenter changes need contract regression tests.
- Run targeted `go test ./path -count=1` first, then `make test` or the relevant `make verify-*`.
- CI (`.github/workflows/ci.yml`): `verify-boundary-contract` + managed `verify-ci-mvp-file` with mock providers — real LLM/weather credentials are out of CI.
- 临时验证目录、日志和构建产物统一置于 `/tmp/workorch-validation/`，不得在项目根目录新增 `.validation-tmp-*` 等目录。需长期保留的受限原始证据放入 Git 忽略的 `.workorch-data/validation/`；验证报告与证据索引统一放在同样不提交的 `docs/validation-reports/`，不存放临时运行数据、原始诊断或凭据。历史证据目录迁移前须同步核对引用，不能直接删除导致索引失效。

## Agent-Specific Runtime Constraints

Before changing runtime behavior, read `docs/00-core/runtime-stage-contract.md` and `internal/modules/kernel/orchestrator/readme.md`. For LLM request rendering, context budget, cache planning, provider adapters, memory recall, or evidence packaging, also read `docs/00-core/runtime-request-cache-note.md`.

Every Runtime change must comply with the four coordinated state machines in `docs/00-core/runtime-stage-contract.md`:

| ID | Machine | Must not |
| --- | --- | --- |
| SM-1 | Run lifecycle | choose next action |
| SM-2 | authority/focus convergence | execute operations |
| SM-3 | candidate/sealed-dispatch transaction | choose next action |
| SM-4 | drive/recovery/projection delivery | rebuild authority |

Change descriptions must identify affected SM IDs, preserve ownership boundaries and forbidden transitions, and add/update transition, invariant, idempotency/restart, stale/duplicate, and budget/guard tests as applicable. Updating one state machine while leaving another’s contract or tests inconsistent is incomplete.

Production path is **Runtime only** (`DriveRuntime` + reducer + sealed dispatch). Do not introduce StagePacket, NextAction, DispatchNextStep, ExecutionContextPatch, auto replan successor, or map-based authority rebuild.

Core runtime must remain functionally neutral. Do not hard-code software development, language stacks, test frameworks, MCP-specific behavior, or business-domain logic into orchestrator core. Put feature behavior in profile, capability, template, or adapter layers. Cross-owner I/O must use EventHub + concrete typed command/result.

Keep the provider-facing LLM cache prefix stable: long-lived system/schema/runtime contracts in `C0`, Goal/DoD definitions in `C1`, declarative capability/governance contracts in `C2`, volatile runtime details in `C3`–`C5`. Treat unexpected `stablePrefixHash` drift as a request rendering bug.

### LLM 处理稳定性：后续开发与优化的核心约束

所有涉及模型的阶段及其上下游组件必须遵守
[LLM Processing Stability](docs/00-core/llm-processing-stability.md)，包括规格生成／审查、规划、操作候选、验证输入、
证据评估、修复、恢复和终态投影。功能正确、可持续推进和稳定拒绝均属验收目标，不能仅以一次成功示例收口。

- 身份、来源、集合覆盖、声明适用性、完整策略合并、版本、预算、权限和状态迁移等可确定事实由所属 owner 的代码计算
  与校验；不得让模型反复猜测这些规则，也不得把纯编译结果当作 readiness、receipt、语义充分性或执行 credit。
- 模型只提出阶段合同允许的最小语义内容；使用闭合 typed 输出、精确输入快照和可追溯引用。prompt、schema、解析器、
  compiler、owner 门禁和展示必须表达同一规则；prompt 调整不能替代组件逻辑修复。
- 原始输出不修补、不改写。模型与确定性事实冲突、语义缺失、未知结果、版本漂移和基础设施失败须按既有合同区分；
  不以多数投票、反复抽样直到 PASS、无界重试、放宽原准则或自动确认获得“稳定”。
- 每项相关变更必须提供固定快照与原输出的确定性重放、真实缺项负例、重复／stale／恢复及必要的并发隔离覆盖。
  模型重复评测单独记录样本、版本、分歧、成本和推进结果；收费 live 只按已有授权执行，不将缓存命中或单次 PASS
  当作稳定性证明。不同 Workspace／Profile 的业务差异保留在各自上下文，不在 Core 硬编码。
- 变更说明明确稳定性影响、可复现输入、失败分类及有界后继路径；尚未接通或验证的部分明确列为未完成，不因写入
  本约束而宣称既有实现已经满足。
