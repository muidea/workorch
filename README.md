# workorch

Status: active

Last Verified: 2026-08-21

WorkOrch 是 local-first 的 Workspace 编排服务。正常 Web 创建输入为 Template、Goal、Resources 和可选用户验收要求；
系统持久化创作输入，派生 DoD，完成六类独立审查，再由用户精确确认并通过 Workspace owner 准入，形成正式 Goal/DoD。
创建和确认均不启动 Run；用户另行显式提交执行意图，通过 TUI-first CLI 或内嵌 Web console 观察收敛，管理 LLM、MCP、Memory 和治理资源。
TUI 不提供创作 wizard，也不接受已退休的直接定义写入。

## Runtime Boundary

Production execution is Runtime-only:

```text
TUI / Web / API
  -> workorchd builds typed RuntimeBootstrap and submits Workspace execution intent
  -> Workspace owner validates definition/scope and forwards the typed intent
  -> Run owner owns SM-1 lifecycle and opaque RuntimeStateRecord CAS persistence
  -> Orchestrator owns SM-2 / SM-3 / SM-4 convergence, dispatch and delivery
  -> capability owner executes one typed operation and returns factual result
  -> Result / Workspace / Run owners acknowledge terminal delivery in owner order
```

The Orchestrator does not own Run, Workspace or Result lifecycle. Capability blocks do not decide evidence acceptance.
Projection and Eventstream are audit/display surfaces, never recovery authorities. Cross-owner I/O uses EventHub and
concrete typed command/result/data only; owner service/repository facades and map-based authority rebuild are forbidden.

The design source of truth is [Runtime Stage Contract](docs/00-core/runtime-stage-contract.md). The implementation source
of truth is [Orchestrator README](internal/modules/kernel/orchestrator/readme.md) together with
`internal/pkg/workorchruntimecontract`.

## Repository Structure

| Path | Responsibility |
| --- | --- |
| `application/workorch` | Binary entry; TUI by default, HTTP/Web with `--server` |
| `internal/services/workorch` | Process lifecycle, local/remote backend, CLI/TUI and agent-session adapters |
| `internal/initiators/workorchruntime` | Memory/file repository provider only |
| `internal/modules/application/workorchd` | Typed bootstrap, HTTP/SSE, execution admission and projection |
| `internal/modules/kernel/orchestrator` | Runtime SM-2/SM-3/SM-4 convergence owner |
| `internal/modules/kernel/{governance,system,workspace}` | Governance policy, startup-default and Workspace coordination |
| `internal/modules/blocks/*` | Stateful aggregate owners and concrete capability owners |
| `internal/pkg/workorchruntimecontract` | Typed Runtime contracts |
| `web/workorch-console` | React/TypeScript/Vite console source |
| `web/consoleassets` | Embedded production console assets generated by the Web build |
| `docs` | Current normative design, product, interface and verification documents |

The baseline contains 22 framework units: 1 Initiator, 5 Modules and 16 Blocks. `internal/services/workorch` is a
process-level shell and is not an additional framework unit. The reviewed responsibility map is
[Component Contract Inventory](docs/01-overview/component-documentation-alignment.md).

## Prerequisites

- Go 1.26.x
- Node.js and npm for rebuilding the embedded console
- an ai-proxy-compatible endpoint when exercising real LLM flows

## Build And Test

```bash
make deps
make fmt-check
make vet
make test
make build
```

`fmt` / `fmt-check` only format product sources. Root `.validation-tmp-*` runtime material,
like `.workorch-data` and `.workorch-workspaces`, is excluded to preserve original validation bytes;
`python3 scripts/test_go_format_source_boundary.py` verifies both read and write boundaries.

Useful aggregate checks:

```bash
make ci
make release-check
make verify-boundary-contract
```

`make ci` runs formatting, vet, tests, boundary verification, the production build and CLI tests. Runtime live-verification
targets connect to an already deployed service; inspect `make help` before running credentialed or destructive scenarios.

## Run

Start the TUI (default binary mode):

```bash
go run ./application/workorch -config-dir config
```

Start the HTTP service and embedded console:

```bash
make run
# equivalent to:
go run ./application/workorch --server -config-dir config
```

Start from a clean file-backed development dataset:

```bash
make run-file
```

`make run-file` removes the repository-local `.workorch-data` directory before starting. Do not use it when that directory
contains data you need to preserve.

After server startup:

```bash
curl -f http://127.0.0.1:8080/healthz
curl -f http://127.0.0.1:8080/readyz
```

The Web console is available at `http://127.0.0.1:8080/console/`. The stable execution ingress is
`POST /api/v1/workorch/workspaces/:workspaceId/execution-activations` with `intent=resume|restart`; run-ID-addressed
create/start/resume mutation endpoints are intentionally not part of the current API. See
[Service API entry](docs/50-product-interface/service-api.md) for command and read contracts.

The first live release supports local-machine operators only. HTTP/Web binds loopback and rejects non-loopback listeners,
proxy-provided identity and cross-origin browser requests; see [Local Operator Access](docs/50-product-interface/local-operator-access.md).
Opening the console does not grant automatic execution or waive exact confirmation/approval.

## Configuration

Configuration is loaded from the selected config directory. The main groups are:

- `repository`: memory/file backend and internal data root;
- `server`: listener, timeout and default dialog settings;
- `runtime`: convergence, retry and capability execution limits;
- `llm`: ai-proxy catalog, default model selection and context budget;
- `webSearch`: provider configuration;
- `governance`: automatic ticket/approval and budget policy.

The `server` section rejects unknown and retired execution-scheduler/watchdog fields. Runtime concurrency and recovery are
owner contracts, not HTTP-server controls.

The LLM owner freezes its active configuration at process startup. Saving LLM configuration changes persisted values for
the next process start; it does not mutate an active owner snapshot or an already sealed Run selection. Secrets are redacted
from read responses.

## Built-In Resources

WorkOrch currently seeds six workspace templates and 36 stage Souls. Templates provide profile policy and initial
definition hints; they do not transfer state ownership to workorchd or Orchestrator. Details are in
[Built-in Default Resources](docs/40-profiles-capabilities/workspace/builtin-default-resources.md).

## Deployment And Verification

Container and persistent-volume guidance is maintained in [Deployment](docs/50-product-interface/deployment.md). Service,
file-backend and deployed verification contracts are maintained in
[Service Acceptance](docs/50-product-interface/service-acceptance.md), while Runtime owner/transition/restart invariants are in
[Core Runtime Verification](docs/00-core/runtime/verification.md).

The most commonly used deployed checks are:

```bash
make verify-service
make verify-ci-mvp-file
make verify-runtime-positive-convergence-live
make verify-runtime-restart-recovery-live
```

These targets expect `WORKORCH_BASE_URL` to identify an already running service unless the target documentation explicitly
says otherwise. Real-provider targets are intentionally excluded from CI.
