# Workorch 渐进式收口与验收策略及第一步功能清单

- 版本：v1.0
- 日期：2026-10-16
- 状态：方案评审稿；本轮不修改项目代码，不执行测试或 live
- 实现参考：`d550e1870ae621313bc4e1dc9031f57ac12c95b8`
- 当前交付范围：重新明确渐进式原则，细化第一步功能与验收；不一次性展开所有业务实现

## 1. 调整后的收口原则

每一步只完成一个用户能够观察、系统能够独立证明的业务结果。先把该结果做可靠，再叠加下一项能力；不把所有业务完整 live、整个 Agent Loop 或全部发布证据作为第一步前置。

采用以下递进方式：

1. 先明确本步功能合同、输入输出和失败状态
2. 用确定性测试验证规则，用真实模块及真实持久仓库验证接线
3. 通过本机生产 Web/HTTP 路径验证本步用户结果及恢复能力
4. 只有本步确实涉及模型或外部系统时，才增加相应替身验证和有界真实验证
5. 每次只纳入已具备前置的下一项业务功能，并回归此前受影响的已验收功能

“本步通过”只对本步范围有效。最终项目目标、尚未交付的 required 能力及其原验收要求继续保留。完整验收可以由逐项可信证据和必要的跨模块关键链验证组成，不要求把所有业务塞进同一个超大 live 场景；已有明确要求的完整场景仍须在对应阶段验证，不能以分步为由取消。

### 与上一版计划的关系

本文件替代上一版“先以 B11.a 验证门禁修复作为当前第一步”的推进优先级，将首个业务结果定位到 Workspace 草稿闭环。B11.a/X05保留为工程验证问题：其中影响本步测试可靠性的内容仍是必要前置；与本步无关的完整 fullflow、真实 provider 和13个部署证据槽不再前置。

STEP01只是本阶段的执行顺序名，对应原 B05 中“创建草稿及服务端找回”的前置子切片，不另建业务模型或状态机。它不继承完整 B05/M3 的六审、合同封存和激活前置，也不表示整个 B05 已收口。本文件不批准绕过仍失败的全局 CI 或最终发布门禁。

## 2. 第一步推荐功能

**STEP01：通过 Web 创建、保存并找回 Workspace 创作草稿。**

### 用户可观察结果

用户选择模板、填写目标及当前创建合同要求的基本信息，点击独立的“保存草稿”入口后，能够获得稳定的 Workspace 标识，并在刷新、关闭重开页面或服务重启后，从服务端列表重新找到同一份已保存草稿，读到保存的输入与真实状态。

生产接口复用：`POST /api/v1/workorch/workspace-authoring`、`GET /api/v1/workorch/workspaces`、`GET /api/v1/workorch/workspaces/:workspaceId/authoring`。本步不调用PUT修订、compile或confirm。

### 本步完成点

- 停在 M1，创作状态为 `authoring.state = draft`
- 草稿已由权威 owner 持久保存，能够独立读回
- 正常创建路径及允许的目录准备已得到明确结果；部分完成不得伪装为完整创建成功
- 没有生成或确认正式合同，没有形成 M3，没有创建 Run，没有发起模型调用或任务执行

此处“草稿已保存”不等于“Workspace 已准备好执行”。当前 `Workspace.State` 可能为 `active`，界面不能据此显示“就绪”；应读取创作状态与创建操作结果。

### 本步不包含

编辑后保存新修订、生成/审查合同、确认/封存合同、完整资源就绪检查、手动或自动激活、任务分解执行、Evidence/Result 全链、合同变更新 Run、删除 Workspace、真实模型与其他业务用途验证。

这些是后续切片，不是从最终目标删除。已有编辑或生成能力也不因本次范围较小而必须全局禁用。

## 3. 第一步需要收口的功能项

| 编号 | 功能项 | 需要达到的结果 |
|---|---|---|
| F01 | 独立的 Web 保存草稿入口 | 提供明确的“保存草稿”动作；仅保存，不隐式调用 compile、review、confirm 或 activation；与已有“保存并生成”含义区分 |
| F02 | 基本输入与校验 | 接收模板、原始目标及当前创建合同要求的基本字段；工作目录可留空，资源引用和额外验收要求可选；检查必填项、模板有效性、字段大小及目录边界；保留输入含义，不截断目标，不要求用户填写运行期证据 JSON |
| F03 | 创建请求身份 | 一次创建具有稳定请求身份；同身份同原始内容重试不重复创建；同身份不同内容明确冲突，不覆盖原草稿 |
| F04 | 权威持久化与独立读回 | 由 Workspace owner 保存草稿及创建来源；返回稳定 Workspace ID；成功后从真实仓库读回核对（当前创建接口成功为201），不以 HTTP 2xx、页面内存或目录存在代替持久化证明 |
| F05 | 草稿详情展示 | 展示已保存的目标、模板及基本输入，准确标记“草稿”；区分草稿保存、目录准备、合同准备和执行状态，不把 active 当 M3 |
| F06 | 服务端列表发现 | 页面刷新或关闭后，不依赖浏览器保存业务输入/requestId，也能从服务端找到并打开已有草稿；不能仅在原页面暂存 Workspace ID |
| F07 | 服务重启后找回 | 使用真实持久后端重启服务后，同一 Workspace ID、草稿输入及创建来源仍可读取；不重新创建另一个 Workspace |
| F08 | 部分失败与结果未知的呈现 | 区分未保存、已保存但目录准备失败、结果未知和正常完成；显示可核对的状态与下一动作，不一律报“创建失败”后引导盲目新建 |
| F09 | 有界恢复与重复提交保护 | 同一页面仍持有原身份和原 payload 时，可按创建协议恢复；页面重开后先发现、核对服务端事实。无法判定时保持“待核对”，禁止无条件生成新 requestId 重发 |
| F10 | 权限与执行隔离 | 生产本机访问边界有效；创建/读取/恢复不越权、不修改用户业务文件、不触发模型或目标业务执行；仅允许本步创建合同内的受管目录/存储操作，不产生Run或有效封存合同 |

F01–F10作为一个小型业务闭环验收，不拆成“先做 UI、再单独做后端”而让中间版本无法集成。具体实现仍可小提交，但本步退出要双端一致。

## 4. 当前代码可以复用什么

后端已存在创建、读取及草稿保存相关接口，创建路径本身不调用模型、compile 或 confirm；已有创建请求身份和初始输入身份可用于幂等保护。输入回读按合同已有的trim规范化比较，内容、顺序和含义不得擅自重排、去重或截断；资源引用只表示已保存引用，不代表资源可访问或已通过readiness。优先复用这些能力及现有 Workspace owner，不新增第二套草稿存储或创建状态机。

本步已核实的主要差距：

1. 当前 Web “保存并生成／恢复审查”动作在 create/save 后继续调用 compile；需要补出真正只保存的独立操作，不能只改按钮文字
2. 当前创作视图没有完整公开创建 requestId/恢复信息；跨页面的结果未知恢复不能假定已完整实现
3. 当前创建先持久化，再准备目录，再读回。目录失败可能已经保存草稿，不能要求自动删除已存事实或宣称零副作用
4. GET/List可按既有owner协议补齐原创建的bindings/index，但不补应用层目录准备；GET读到draft本身不证明目录已准备完成。展示和恢复判断必须能追溯真实创建阶段

本步允许的资源变化是草稿元数据及创建合同内的受管目录准备。禁止借恢复删除未知归属的目录或清空持久数据。

### 最小组件范围

- Web Console：纯保存入口、详情、列表发现、错误与恢复提示
- workorchd：生产 HTTP 路由、请求校验、创建/读取结果投影
- Workspace：草稿与创建来源的唯一 owner、幂等和权威持久化
- 已有目录/存储能力：只接入创建所必需的路径，不扩展业务执行
- Run/LLM：本步仅观察“未产生 Run、未发生模型请求”的边界，不要求改造其执行能力

不为本步重构22个组件，不改 Agent Loop，不引入新执行权限或泛型跨模块消息。

## 5. 第一步验收清单

所有用例使用隔离的数据根与明确受管目录。测试通过必须附实际记录；下表目前都是待执行要求。

| 用例 | 操作或故障 | 必须观察到的结果 |
|---|---|---|
| A01 正常保存 | 从生产 Web 入口提交合法输入 | 返回一个稳定 Workspace ID；独立读回与合同规范化后的保存输入一致；inputRevision=1、inputHash非空、创作状态draft。目录留空时默认解析正确；指定已有目录时保留哨兵文件，正常创建阶段结果明确 |
| A02 重复提交 | 重复点击或重放同一 requestId、同一初始 payload | 返回/找回同一 Workspace；不新增重复草稿；不会触发生成合同 |
| A03 身份冲突 | 用同一 requestId 提交不同初始内容 | 明确冲突；原草稿不被覆盖；不创建替代 Workspace |
| A04 输入不合法 | 无效模板、超长目标、必填缺失或越界目录 | 说明具体错误；不静默截断；不形成可误认为已成功完成的记录；按实际已发生阶段报告状态 |
| A05 刷新找回 | 正常保存后刷新页面 | 从服务端重新加载同一草稿，不依赖旧页面内存 |
| A06 关闭重开 | 清空页面会话后重新打开列表 | 能发现并读取已保存的同一 Workspace；不依赖 localStorage、sessionStorage、IndexedDB 或业务 cookie |
| A07 真正重启 | 正常保存后停止并启动新的服务进程，使用同一持久后端 | 草稿和创建来源仍在，ID不变；不能用仅重建对象的测试替代此项 |
| A08 持久化失败 | 在权威写入前注入存储错误 | 不显示“草稿已保存”；能够判断未成功的阶段；不得伪造记录或有效合同 |
| A09 保存后目录失败 | owner 已保存，随后目录准备失败 | 保留原 Workspace；准确显示已保存及目录未完成；通过协议允许的同身份恢复，不把 GET draft 当目录已就绪 |
| A10 响应丢失 | 保存后丢失响应，分别测试页面仍在与页面已关闭 | 先核对原操作；已知事实不重复创建。具备原身份/原 payload 才重放；无法确定时明确待核对，不承诺本步实现任意断点自动恢复 |
| A11 页面和读写隔离 | 旧请求晚返回、新页面会话已打开；重复查询详情 | 旧响应不覆盖新会话；读路径不得改变原输入、生成新合同或启动执行。允许现有owner协议补齐原创建的bindings/index，必须保持同一创建身份且不重放业务effect |
| A12 访问与零执行 | 拒绝非法来源请求，并观察整个保存/读取/恢复链 | 访问拒绝先于业务修改；与本创建相关的 provider 调用、compile/confirm/activation及 Run 创建均为0；不改用户业务文件 |

A09在原身份和原payload可用、临时故障解除后，必须恢复同一Workspace至本步成功；不能永久停在“待核对”仍算该恢复正例通过。A10中能够可靠核对原事实的分支，同样必须按原身份完成恢复。只有确实无法可靠重建原身份或owner事实仍不确定的分支，才允许安全停在“部分完成／待核对”；这不能冒充正常创建完成。恢复成功与安全停止分别记录，不混成一个PASS。

## 6. 验收层级与退出条件

### 第一层 规则与合同

验证输入边界、请求身份、同键冲突、状态投影、纯保存动作以及无隐式执行。可以使用定向单元测试及故障注入，不调用真实模型。

### 第二层 真实模块集成

使用真实调用方、Workspace owner、生产 typed 路径和真实持久仓库，证明 create/read/recover 的结果及写入切点。不得用直接修改仓库、伪造草稿记录来代替公开创建成功。

### 第三层 本机 Web 功能验收

通过生产 Web/HTTP 路径实际完成保存、列表找回、关闭重开和进程重启。这是本步局部实机功能验收，不是整个项目的 SG3/live 通过，也不要求公网部署。

本步不涉及模型调用，因此既不需要真实 provider，也不需要为了凑完整链而增加 mock provider。后续切片出现模型依赖时，再分别增加确定性替身覆盖和明确范围的真实模型验证。

### 本步退出必须同时满足

- F01–F10有对应实现或可证明的既有能力，A01–A12取得本步适用证据
- 正常保存能独立读回，刷新/关闭/重启能找回同一草稿
- 重复、冲突、部分失败、unknown与迟到响应不会制造重复事实、假成功或意外执行
- 本步新增和受影响路径完成累计回归；当前无关的全局失败仍单独登记，不能宣布全库 CI 通过
- 证据绑定同一候选提交、配置和测试数据范围

退出结论固定写为：**“Web 草稿创建、持久化与找回闭环通过。”**

不能写为“Workspace 创建到 M3 已完成”“Agent Loop 已通过”“全部业务可 live”或“项目可发布”。

## 7. 本步验收产出

只要求一份简洁的 Markdown 验收记录及其原始证据引用，内容包括：

1. 本步实际代码 SHA、构建/配置及持久化后端
2. F01–F10实现对应、必要生产双端和受影响文件
3. A01–A12逐项 PASS/FAIL/BLOCKED/NOT_RUN，真实操作与观察值
4. Workspace ID、创建身份、持久记录及独立读回；原始输入按访问权限保存
5. 重启前后进程身份、草稿身份与数据核对
6. 相关模型/执行请求和 Run 数量为0的观察证据
7. 已知局部问题、无关全局失败、允许进入的下一切片；不得把未验证写成PASS

本步不要求13个部署证明槽、完整任务 Evidence/Result 包或所有用途的 live 报告。后续应逐步积累对应证据，而不是先搭建全部最终验证设施才允许第一步退出。

## 8. 哪些调整需要 ticket

按用户要求重排收口顺序、拆分功能批次、只验证本步范围，并保持未交付目标可追踪，属于工程计划调整，无需为此虚构目标变更 ticket。

若为了通过而删除原目标、降低原验收标准、改变合同约束、把部分完成改称最终完成，必须发起 ticket，说明原因、差异、影响和替代证据；不能借“渐进式”直接放行。涉及已封存业务合同的变更仍按既定 exact approve、新 Definition、新 Run 规则处理。
