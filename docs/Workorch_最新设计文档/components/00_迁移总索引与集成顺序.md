<a id="contract-reading"></a>
### 合同引用约定

以下CT标识引用固定源码目录，不是新增API名称；标为“目标”的边仍需实现/接线或逐调用方核验。M3/M4、完整ticket变更及新增字段必须在具体合同目录以目标提案单列，不能反写成现存符号。

每个MIG入出边表只选迁移影响最大的边，其owner合同页的全topic是完整接口范围。Initiator和System没有自身业务topic，按CF00描述真实装配或消费边。具体合同目录负责实际guard、Result arms、错误映射及兼容；MIG中的自然语言用例不会成为第二套API定义。

## 3. 集成顺序只从总纲导出

1. 在[总纲能力批](../Workorch_逐项收口总纲与首项方案.md#batches)选择当前可进入的B批，固定相应C主题、实际源码/数据/配置版本和适用边界
2. 选取本表相关MIG的最小必要改动；读取其保留/新增/移除、具体路径、合同入出边、相邻owner及中间稳定态
3. 破坏性接口两端、schema读写、活动fence或全局生命周期必须成组切换；准备代码可分提交，不将不兼容混合态视为可发布能力
4. 将[具体合同](../contracts/组件具体合同目录.md)对应case和MIG特有断言实例化到[验收规格](../validation/验收规格.md)，按总纲适用SG层级收集证据；最后Web批才要求完整SG3
5. 只更新总纲的单一状态台账。新增实现、测试文件存在或局部PASS不能自动把整个B批/组件标为收口

Workspace纯组织迁移与业务语义调整分开验证。Base任务API如果要求全部实际调用者同时适配，就必须保持该广度；这不等于同时重写22个业务域。没有某能力需求的模板不强行调用该owner，使用替代provider/fixture时标出证明上限。

## 4. 每项迁移留下什么

每个MIG保留：当前到目标角色；固定源码复用证据与具体路径；新增/适配/移除；真实合同ID的生产消费边；总纲批依赖；步骤及稳定中间态；兼容、故障恢复与回退；安全约束；fixture与独特验收差分。实施后在对应正式批记录补实际改动和证据，不另建执行账本。

旧数据缺少来源、授权或证明字段时保留历史不足，不能通过默认值补造PASS。路径移动默认保持owner、ID及journal；用户源数据、共享、临时与正式交付资源按归属处理。M3/D1/D2既有目标沿用；若需修改目标、验收或约束，走完整ticket及最终精确候选批准，不能以迁移名义改变。

修订记录：v0.3删除重复X合同、G门禁和阶段顺序，转为权威导航；22份MIG补明确差分、稳定态、精确合同边与验收引用。当前交付是候选方案，不是执行验收报告。

修订记录：v0.4（2026-10-12）按固定SHA重核全部22角色及当前路径；Workspace提升已落实，生命周期/合同纯包已有增量改为复用与回归，产品目标和既定验收不降级。
