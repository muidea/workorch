## 1 共用身份与事实边界

1. AuthenticatedPrincipal来自可信服务端鉴权，包含actor、代表谁、权限依据及授权范围；客户端提供的principal文本、requestId或permitID不能自证权限
2. WorkspaceID、InputRevision、CandidateRevision/hash、DefinitionRevision/hash、StartupInputHash、ConfigHash、资源/能力owner revision、Run StateRevision、runtime binding/generation分别校验，不合并成一个version
3. 每一intent与fact保留自己的持久身份、content hash、owner revision及causation；返回prepared/accepted不等于materialized/RunCreated。UI阶段是这些记录的派生，不新增万能状态机
4. 同scope幂等身份同内容返回原事实和最新完成进度；异内容返回NC_CONFLICT。仅因网络超时无法判明提交结果时为unknown；已有owner明确失败保留FAIL及原phase，不因诊断读取失败降为unknown。先查原身份，不换requestId生成新Workspace、Definition或Run
5. 各owner提交自身事实及可恢复关联标识，再投递事件。普通审计/SSE迟到不能改写业务结果；安全合同要求先留痕的动作在留痕失败时阻塞。敏感源文和凭据只用受控引用，不进入普通日志或默认导出
6. 已有公开authoring、DefinitionAuthoringCreation、prepared→materialized确认journal、WorkspaceStartupInputContract、WorkspaceActivationAdmission及Run Start/Restart仅作为复用参考。新增证书、grant、adoption等逻辑记录复用既有owner存储，不要求新增服务/组件或平行journal
7. 固定目标字段缺失即返回对应阻塞；不能默认无限期限/预算/权限。TTL、预算和policy取已批准配置/用户授权的精确版本；本文不擅自设产品常数

## 2 NC00 创建和定义封存

NC00吸收原统一模型§5.8及Web§3.2/§5.3的软件协议；来源/义务业务含义仍见统一模型§4。下列phase是恢复协议标识，不声称需要添加对应Go枚举。

| Phase 与intent | 接收owner及必需输入 | 持久fact与输出 | 幂等和崩溃恢复 |
|---|---|---|---|
| C0 CreateAuthoring | Workspace；可信主体、creation request ID、完整原文、template ref、资源/交付位置/约束及规范化规则版本 | 稳定WorkspaceID、输入原文/规范化hash、固定模板解析结果、creation进度；M1仅在身份/草稿可靠保存后成立 | request同内容同Workspace；异内容冲突。metadata、binding、index、目录各步骤按after-image核对，读到metadata不代表完整恢复 |
| C1 PrepareResources | 各资源owner；Workspace creation operation、确切目标/作用域/管理归属、expected resource revision | 目录/绑定准备receipt、可读写边界及未完成项 | 按原operation续做；现有用户内容不覆盖。共享managed-configs不被单Workspace独占清理；无法证明独占且未被改动的临时项不自动删除 |
| C2 ReviseInput | Workspace；expected InputRevision、修订内容、source refs、必要的change ticket依据 | 新InputRevision及明确差异，受影响candidate/review/admission引用失效 | CAS拒绝旧页覆盖；涉及已设定承诺的实质变更走NC04，不以草稿为由绕过 |
| C3 GenerateCandidate | Workspace组织authoring；固定input/template/resource/config hashes、provider请求身份和scope | provider提案及原文审计、owner编译canonical candidate、候选revision/hash | provider不直接写正式Goal/DoD；旧输入生成晚到只入对应历史，不覆盖当前版。authoring可调用获准provider且费用归Workspace/authoring账，不虚构Run或runtime证据 |
| C4 ReviewCandidate | Workspace；exact candidate、六类适用范围清单、review结果与出处、declared verification | 每类PASS/FAIL/UNKNOWN/有理由N/A及逐要求/义务覆盖事实；只在required审查全集齐备时可确认 | 仅六个非空PASS不充分；相同review identity不同内容冲突。review与candidate/config来源变动不匹配即过期 |
| C5 AcceptCandidate | Workspace；exact input/candidate/review set/模板等hash，人工confirm identity，或NC02 PolicyAcceptanceReceipt | 精确接纳事实，标明human exact或authorized policy；不生成Run | 先查已有确认，后处理当前修订；响应丢失不要求重签同一已提交候选；内容改变必须重新接纳 |
| C6 MaterializeDefinition | Workspace；确认身份、完整Goal/DoD after-image、Definition hash、预期前态与manifest | 同一ConfirmationJournal prepared及各物化进度；整组内容与commit generation一致后materialized，返回DefinitionRevision/hash和seal receipt（M2） | prepared后崩溃重读相同after-image逐项对账；旧用户编辑/混代/hash冲突停在明确恢复冲突，不盲目覆盖；未过整组可见性屏障不得读取为有效seal |
| C7 ReadCreation | Workspace只读查询；有权主体、Workspace/operation ID、精确版本范围 | 各阶段已提交fact、仍待完成项、恢复入口及可用动作 | 查询不是转换；部分失败保留既有ID和已提交阶段。确认后关页不能撤销seal；目录失败不新建Workspace |

正式定义包含来源、原子要求、独立义务、判据、覆盖映射、验证政策及资源/配置绑定；shared Criterion/Task/Evidence合法，不能把source obligation→CWI强行收缩为1:1或吞掉原义务。各CWI仍保持一个primary source item，完整覆盖映射另行表达。完整Goal锚点不要求补造重复DoD，但不能以保留全文替代提炼全部承诺。

创建对目录采用当前受支持的安全策略：路径穿越、符号链接逃逸、现有内容冲突、只读/越权返回明确错误；验证与使用之间必须有owner范围/fence保障。内存backend不得宣称满足崩溃后恢复；临时演示模式须显著区别。普通导出失败不撤销seal，导出是否成为required须另有产品决议。

#### NC00 数据保真与页面恢复边界

- 原始Input/provider document/失败cause按原字节保存，记录byteCount、SHA256、来源与scope；协议编码可逆，规格规范化保留独立结果，不覆盖原始诊断。不得以脱敏、清洗、替换字符或摘要冒充原文
- cause存储/传输超界返回明确未保存/未传递原因及原hash/字节数；诊断容量耗尽不能编造可查询diagnosticID。部分内容不是完整数据，诊断不可读不改变已知失败；尚无实际request reserve的前置失败不能伪造成已调用provider或消耗新额度
- 原文通过owner受限读取显式取得，普通查询只投影metadata。bytes/hash/身份不匹配即拒绝展示；非UTF8保原bytes，不能替换字符后声称原文。原诊断不进Git、默认导出或通用日志，且不含无关凭据/live配置
- Web业务输入、事务重放身份及服务端数据仅页内存暂存，不使用localStorage/sessionStorage/IndexedDB/cookie等浏览器持久机制。关闭/刷新会丢未保存编辑与页内重放身份，必须明确提醒；服务端已保存事实及确认恢复依据由owner查询，关页不取消已发送事务。重新打开先核对服务端事实，不用缓存旧payload重开事务

停止生成是独立取消intent，以owner最终事实为准；关页/断网不是取消。删除、放弃草稿及清理遵循各自授权与Workspace删除journal，不能作为创建失败的隐式补偿扩大删除范围。

## 3 NC01 M3 readiness certificate与失效

### 3.1 输入和输出字段

RecordReadiness接收精确WorkspaceID、seal receipt、DefinitionRevision/hash、StartupInputHash、Definition admission fact、ConfigHash及解析规则版本、resource binding set/hash、capability requirement set、创建准备manifest、各owner检查receipt和鉴权上下文。Workspace向能力owner查询只读/获准检查；检查不执行目标业务effect，authoring既有provider调用与检查成本如实归账。

ReadinessCertificate（目标记录）至少保存：

- certificateID/schemaVersion、WorkspaceID、definition revision/hash、startup input hash、有效config/template/profile/policy hashes及各来源revision
- 资源依赖集：owner、resource/binding ID、observed revision或精确hash、版本策略、访问/权限scope、可用性检查receipt；没有稳定revision的外部资源必须使用有有效期及适用范围的观察token，不能用缺revision当“永不变化”
- required capability集合：operation/contract version、owner、目标环境/访问边界、判据、PASS/FAIL/UNKNOWN、原始检查receipt、checkedAt、expiresAt/lease条件及失效触发器
- 创建after-image完整性、目录/索引/绑定事实及准入receipt、有效性计算规则版本、聚合checkedAt、最早expiresAt、dependency set hash、各owner实际revision
- status为当前判定语义（valid、stale、blocked等目标值），原因与受影响依赖；原证书不可改写成不同观察，失效事实append并产生新证书版本

CreationCompletionReceipt另存completionID、WorkspaceID、creation epoch、firstSatisfiedAt、certificateID/hash、exact seal/startup/config绑定及`noRunAtCompletion=true`的权威断言。它不是当前readiness可变缓存。M3只在C6屏障完成、全部required准备/准入/检查均PASS且尚无Run创建事实时，Workspace在同一owner CAS中提交；记录先于任何ActivationPermit提交。首次M3身份不会因之后资源掉线、候选改版或新证书而重新生成。

### 3.2 有效性与重查规则

| 改变/时点 | 当前资格处理 | 历史事实处理 |
|---|---|---|
| DefinitionRevision/hash或StartupInputHash改变 | 对新定义必须重新形成精确admission和证书，不沿用旧绑定 | 旧seal/M3及旧证书保留；不得标新定义已就绪 |
| ConfigHash、template/profile/policy或验证/能力合同版本变化 | 若使用已固定快照且运行权限仍允许，按原快照检查；若有效启动配置改变，旧证书stale，重编译/重查实际依赖 | 不热改旧Run或旧证书；涉及已设定承诺时先NC04 |
| 资源内容revision、版本策略、位置/访问scope、凭据授权或能力owner revision变化 | 命中dependency set即stale/blocked；按影响重查，UNKNOWN不算PASS | 历史资源receipt保留，不能用新值覆写旧观察 |
| 证书/任一必需检查到期、owner失联、检查无法确定 | 不可激活；显示具体expiry/unknown依赖 | 不撤销历史M3，不伪称新建从未完成 |
| Start受理时 | 服务端核对精确最新依赖/lease及适用证书；页面ready不能替代本次检查 | 如果已存在同一intent的Run，按NC03返回原事实，不把重放变成新Start |
| Run已创建后资源/授权改变 | 由Core及operation owner阻止不再满足前置条件的新effect | 启动证书只证明受理时条件，不承诺之后永久可用 |

证书expiresAt取所有必需检查和批准政策中最早边界；没有可确定有效窗口/版本时只能当次重新查询并产生有界单次检查，不自行给长期TTL。通过状态变动通知尽快失效，但不依赖通知必达：启动前仍比较owner事实与expiry。查询和Run创建间资源可变性通过实际owner lease/fence或操作前重查治理，不谎称跨外部系统原子快照。

### 3.3 错误、幂等与恢复

NC_READINESS_STALE、NC_CAPABILITY_UNSUPPORTED、NC_RESOURCE_UNAVAILABLE、NC_PREPARATION_INCOMPLETE、NC_CHECK_UNKNOWN分别返回受影响ref、观察时间、可恢复条件和下一步，不合并为普通“创建失败”。certificate request同binding/检查集重放返回同证书；新观察形成新identity。M3写入后丢响应查completionID返回原回执；M3前崩溃不从页面缓存补造完成。完成已存在且已有Run时查询返回历史M3及真实Run，不能再次断言当前Run为0。

## 4 NC02 有界自动授权和撤销

### 4.1 授权的持久归属与内容

Workspace保存BoundedAuthorizationGrant及单调revision；GrantAuthorization意图必须来自有权用户/明确获授权主体，不能由LLM、reviewer或默认自动化政策自批。它可在同一个Web提交中授权候选政策接纳和一次初始激活，不要求已经授权后再重复人工点击。默认没有该grant即手动模式。

| 字段组 | 必填目标语义 |
|---|---|
| identity与主体 | grantID、WorkspaceID/creation scope、grant revision、request/content hash、issuedBy/representedPrincipal、delegation/permission basis、createdAt |
| 内容边界 | exact original input hash/revision、template/config/policy版本或明确受限选择规则、资源集合及读写/执行/网络scope、允许动作；candidate可接受谓词及检查方法版本 |
| 接纳范围 | 允许哪类candidate政策接纳；必须保留的目标/required/判据/约束；不得授权未知范围的目标缩减。候选实质改变既定承诺必须NC04最终精确approve |
| 执行范围 | 一次初始activation或一个明确change successor intent；目标definition最终精确绑定方式、预算上限/累计scope/已知authoring成本、风险等级与另需Run-bound Approval的动作 |
| 时间与次数 | validFrom、expiresAt（来自明确授权/已批准可见政策）、maxUses及使用identity；不能因恢复、页面刷新、首Run终态自动续期或恢复次数 |
| 撤销与历史 | grant revision、revokedAt/reason/actor、所取消的尚未接纳intent，以及已接纳intent/Run引用；原grant内容不可被撤销记录覆盖 |

缺期限、预算scope、权限或候选边界且没有明确批准的可见默认值时，不自动执行；告知缺项，让用户补充所需授权，而不是再次询问已决manual/auto路线。Grant也不能把普通合同确认升级为无限仓库修改、付费或外部发送权限。

### 4.2 精确政策接纳

EvaluateCandidatePolicy输入grantID/revision、最终candidate revision/hash、review coverage set/hash及精确source/config/resource绑定。Workspace确定性校验主体权限、grant有效性与可接受谓词，全部成立才持久PolicyAcceptanceReceipt，记录actualAcceptingActor、grantRef、policyVersion、检查事实、exact candidate及acceptedAt。人类精确confirm与政策接纳在回执/审计上必须可辨。

UNKNOWN、越范围、到期、撤销、配置授权基础失效或must-human问题不生成接纳成功；返回NC_AUTH_*及待决定项。政策接纳后仍按NC00同一confirmation journal物化；不得让自动路径绕开六审覆盖、可见性屏障或M3。发生候选实质变化必须重新接纳；涉及已设定承诺还须NC04而非自动缩小目标。

### 4.3 接纳与撤销的确定竞态

Workspace把grant revision变更、revoke与NC03的CommitActivationPermit纳入同一owner串行CAS决定。网络到达先后、前端点击时间和跨owner事件顺序不构成授权顺序。

- 撤销CAS先提交：后续permit提交因grant revision/status不匹配而拒绝；仅prepared的intent/RunID预约不允许Run物化
- permit提交先成功：同一原子写集消费本次use、记录exact intent/definition/runID与permit、固定slot reservation，表示这一次精确Start已在有效期内被接纳。之后的授权撤销阻止未接纳动作，但不得谎称已接纳Start从未发生；撤销响应返回该intent及Run/待物化状态，并给出独立取消路径
- grant在permit commit前过期必须拒绝；commit后到期不将恢复同一已接纳Start变成新授权，不允许生成新Run或重置预算。动态权限撤销仍在运行/能力操作前强制生效；如已接纳尚未物化的Start因危险撤销不可调度，可恢复出同一Run的受阻/取消事实，不能丢弃identity后重建
- revoke响应丢失重放返回原撤销序列及已接纳清单；旧grant version永不重新激活。grant内容扩展须新明确授权，不能以revision升级静默增权

这是精确Start受理与物化分离的线性化边界，不宣称已有跨owner事务。仅Workspace持久permit可授权Run执行同一个物化命令；Run本身仍唯一创建Run。运行危险操作的Approval独立且必须绑定Run/operation。

## 5 NC03 initialactivation与Run唯一物化

### 5.1 输入输出与稳定身份

首次激活逻辑键为`(WorkspaceID, initialactivation)`，由服务端创建并永久映射到一个稳定intentID；具体存储键是目标设计而非当前Go字段。M3 receipt和精确定义是intent payload，不把“每次新证书、新页面、新requestId”都当新首次激活。不同manual/auto传输请求映射同一逻辑键。首次真正接纳前若定义变更，原prepared payload须被显式supersede并通过NC04及新的明确授权，不允许异内容请求静默覆盖；只有一个payload能取得首次Run。

ActivationIntent最少包含intentID/type（initialactivation或明确后继/再运行）、WorkspaceID、exact Definition revision/hash/StartupInputHash、M3 receipt及当前certificate、执行主体/授权依据与grant revision或本次手动执行授权、预算及资源scope、expected slot generation、payload hash和causation。手动点击提交精确当前显示版；服务端仍验证同等约束，不把点击过时页面视为批准任意新版本。

Run返回StartResult：intentID、RunID、绑定定义/启动快照、Run StateRevision/真实状态、materialization/activation receipt。页面可另外读取有限可用动作投影；该投影不是通用NextAction dispatcher，不驱动领域转换。重复响应返回原Run当前状态（可已terminal），不能只返回一份过时“启动成功”文本。

### 5.2 phase与原子提交

| Phase | intent与guard | owner提交fact/输出 | 中断或重复处理 |
|---|---|---|---|
| A0 ResolveIntent | Workspace解析manual/auto请求；先查询initialactivation映射 | 已有committed intent/Run则直接返回原结果；否则稳定prepared intent | 首个Run已terminal也不重新验收“创建第二Run”；异内容冲突展示已有对象 |
| A1 PrepareStartIdentity | Run依据稳定intent预约确定RunID，尚无Run生命周期实例；Workspace核对M3先已存在 | Run的幂等identity预约事实；不是RunCreated，不得把它计作M3时已有Run | 崩溃重查预约；未获permit不能执行；不会新造第二ID |
| A2 CommitActivationPermit | Workspace验证M3、exact seal/admission/当前certificate、有效手动授权或grant、预算/资源、无活动资格及handoff屏障；CAS版本准确 | 原子写intent accepted、授权use消费、exact RunID/payload permit、slot reservation/generation及可重投递标记 | revoke/expiry竞争按NC02；CAS失败不消费use。提交后丢响应按intent查permit，不重新授权/发第二permit |
| A3 MaterializeRun | Run消费可信Workspace permit，校验RunID、intent、payload、fence、snapshot和协议版本 | 唯一pending RunCreated/StartResult，冻结exact启动输入；不激活、不drive、不dispatch effect；重复permit返回同Run | 不信任UI自报permit。物化中断按原identity补齐，冲突停机诊断，不换ID。若权限动态撤销则不发新effect，保留同Run受阻/取消事实 |
| A4 ConfirmSlot | Workspace接收exact pending RunCreated receipt，校验reservation generation/RunID | 同Run占有活动资格的关联及slot ACK；这是slot事实，不是Run已active | Run创建后ACK丢失先向Run查询；unknown不能释放slot后重启。旧ACK不得覆盖新generation |
| A5 ActivateRun | Run核对pending身份、exact slot ACK/permit、启动快照与动态安全条件；后继还要求NC05双端lineage已完整 | Run owner执行合法pending→active转换，持久RunActivated fact及StateRevision | 缺slot ACK/lineage或安全条件时保留pending/合法受阻状态，不drive；重复激活返回原事实，不重置Run |
| A6 AcceptRuntimeActivation | Orchestrator接受matching RunActivated fact，校验Run/Definition/bootstrap/activation binding及自身恢复事实 | 初始化/恢复同Run runtime，先fresh workspace_full reconciliation；符合Core才可drive/effect | Run已active不代表runtime已接纳；中断按原身份恢复。旧fact、旧generation和缺失跨Run屏障不得启动新effect |

Run准备身份与真正RunCreated必须在查询/审计明确分开。默认手动流程停在M3，不执行A1–A6；明确自动授权可在同Web提交后独立进入以上阶段。

### 5.3 pending取消和未激活失败的恢复出口

危险撤销、明确取消或启动失败可能在A3已有pending Run、A4 slot ACK之前，或A5已active但A6尚未初始化runtime时发生。只有用户明确取消或已冻结授权政策将这一次精确撤销映射为合法取消意图时，才进入以下行政收尾；普通资源/准入失败保留typed诊断和blocked状态，提供恢复/明确取消入口，不能为腾slot伪造取消授权。此分支不能靠页面直接置terminal，也不能把pending reservation永久留作唯一出口。

1. Run核验合法取消依据后，以原intent/RunID记录明确cancelled意图、授权/撤销来源、原因和expected StateRevision；停止该Run的激活资格。不得据启动错误擅自给pending写failed；只有既有合法SM-2 sealed failure才可走failed终态，有既存runtime时由Core终止事实确定合法结果。若仍未物化Run，保留已接纳intent/预约身份并按同ID完成可审计的pending实体及终止处理，不抹掉已受理Start
2. 未初始化runtime时采用Core目标扩展`TGT-NC03-AdministrativeCloseout`；本文PreparePendingActivationTermination只是其语义操作别名，完整versioned administrative-only shape、authority-source=`RunAdministrativeIntent`、SM-4转换/编译规则均只由Core维护。适用于pending或active但尚未正常初始化且有合法取消意图；不得把“没有aggregate”或“曾/未RunActivated”单独当零effect证明。Run/Orchestrator须以同Run initialization/dispatch write fence、birth/init-commit marker/opaque generation及权威dispatch/claim inventory证明无业务handoff，按Core的expectedRuntimeRevision=0 CAS建立admin-only上下文。normal init若先赢，fresh-load转正常TerminationRequested；证明不足、腐坏或不兼容load保持typed blocked/fail-closed，不合成终态、不释放reservation。行政上下文零provider/session/dispatch/effect/coverage，单向形成cancelled材料，required未验证且不授credit，永不能转业务，不伪造SM-2 AuthoritySnapshotID/DefinitionRevision/EvidenceRevision跨过guard
3. 该目标材料仍遵循Result持久ACK→Workspace exact terminal-handoff ACK（保留reservation/handoff屏障）→Run按合法SM-1 pending→cancelled或active→cancelled转换持久terminal的顺序；已有runtime则以Core合法终止转换为准。现有类型若无行政终止分支须按此目标接收合同显式扩展，不以UI/应用直接写Run状态旁路实现
4. Workspace在收到或主动查询到同intent/RunID、reservation generation及exact terminal/Result证明后，仅释放这一代reservation/handoff。它可以接纳这一终止路径的receipt，不要求先把已取消Run补做A4/A5正常激活。未知、错generation或缺结果证明不释放
5. 永久保留initialactivation→原Run和取消/失败结果。随后同首次请求仍返回原terminal Run；释放slot只允许用户另行明确提交新的restart/reexecute意图，不自动再Start。响应丢失按原关闭/Run/Result身份重入，终止事实不代表旧未知成本为零

PreparePendingActivationTermination和NC05-LATE同为目标扩展，实际接收topic/类型须在组件目录映射；不得把尚未有实现证据的路径标为已有能力。

### 5.4 失败与终态后迟到重试

- M3/定义有效但readiness或资源不符：NC_READINESS_STALE/NC_ACTIVATION_BLOCKED；保留创建完成历史，原intent保持未接纳，可在同payload下检查恢复
- grant/权限无效：NC_AUTH_EXPIRED/REVOKED/SCOPE；不创建Run。补充授权必须精确绑定同intent及合法payload，不产生另一个initialactivation
- 传输超时、Run创建ACK未知：NC_RESULT_UNKNOWN，返回intentID和查询入口；从Run authority读到结果前不声称无Run、不释放reservation、不另发Start
- 同一initialactivation已materialized且Run已terminal：任何迟到manual/auto retry或completion回调都返回该Run，slot空也不能再次物化。真正再运行必须明确新的restart/reexecute intent，并遵循Core；普通Restart可以绑定相同Definition，不强制变更ticket
- 初次激活永不可由日志保留期限清除后重新推断“没运行过”。Workspace删除后保留必要tombstone/intent身份，旧请求不得复活对象

## 6 NC04 reasoned ticket到精确定义采纳

### 6.1 ChangeProposal的完整输入

ChangeProposal复用Decision的ticket/resolution持久owner，目标payload至少包含：

1. TicketID、WorkspaceID、明确的可选predecessor RunID、current Definition/Input revision/hash、受影响稳定item refs、proposal revision/hash、提出主体及依据
2. 完整reason：触发事实、发现过程、根因/未知点、可核对证据、为何需调整；“实现难/测试不过”不能单独完成原因。不确定项如实标明
3. before/after逐项语义差异、原目标保留情况、备选方案及不采用原因、不改变的后果与可以安全继续的范围
4. 影响集：来源/Requirement/Obligation/Criterion/VerificationPolicy/覆盖审查与mapping、配置/资源/环境/交付、已有plan/CWI/证据/closure。分别标保留、重查、失效/重开、未知
5. 已发生/在途/unknown effect refs、confirmed/unknown-reserved成本、累计预算/风险影响及另需授权；不得将“新Run”写成清零方案
6. 修改完成的exact final candidate revision/hash、审查结果及适用范围、所需决议主体/权限scope、采用路线/安全交接条件、可选同时提交的有界新Run执行意图

最终候选及影响分析必须在approve前形成。原因、语义差异、候选、目标版本或重要影响集变化产生新proposal revision，原批准不能套用。UI可先展示open草案，但不把不完整草案标成可无条件应用。无需已产生代码/测试文件才允许修改定义候选；这里只是合同修订。

固定有向顺序是用户exact approve选择→Workspace definition-scope preflight→（runtime-bound才需要）Orchestrator matching acceptance→Decision formal commit/ACK→Workspace adoption→原journal物化。preflight不依赖未来resolution/adoption，消除循环依赖。无Run不造Run；DefinitionScopeValidation、DefinitionAdoption与runtime acceptance分别留痕，不能互相冒充。

### 6.3 无Run、活动Run及terminal前驱

| 场景 | 必需采纳与结果 |

| 尚无Run | Decision先持久Workspace/Definition-scoped ticket/用户选择，Workspace以source Definition/Input revision/hash做D2B校验，Decision D2C formal commit后Workspace才做D3 adoption。明确记predecessor=null、matchingRuntime=not_applicable。新Definition封存后通过M3/当前证书和执行授权创建首个Run，绝不伪造Run进行匹配 |

### 6.4 错误与补偿限制

NC_REASON_INCOMPLETE、NC_CANDIDATE_NOT_FINAL、NC_REVIEW_INCOMPLETE、NC_DECISION_SCOPE、NC_DECISION_STALE、NC_ADOPTION_CONFLICT、NC_MATERIALIZATION_CONFLICT、NC_HANDOFF_BLOCKED分别携带准确phase、owner事实、受影响refs、是否可重试及所需动作。不得用统一“approval失败”掩盖已获批准但未物化。

## 7 NC05 安全交接与后继lineage

NC05只细化合同变更后的跨Run衔接，普通same-Definition Restart的私有状态机仍见Core。new Definition来自NC04，new Run必须已经获得精确执行授权；用户可以一次“批准此版并按所示范围执行”给出两项意图，不需重复手动确认。

尚无任何历史Run的无前驱分支，H0/H4必须映射回NC03同一个`(WorkspaceID, initialactivation)`，ticket/adoption只是该意图payload的版本/因果信息，不新增change-firstRun键。若已有未接纳旧payload，按NC03显式supersede保留历史；若已接纳/已产生首Run，即使slot空也不能标predecessor=null或另建初次激活。已有历史Run必须解析真实前驱/lineage，不能从空slot推断“无历史”。已有M3绑定旧Definition时保留原M3，new Definition使用当前NC01证书和精确授权，不伪造另一份首次M3。

### 7.1 Handoff输入及证明

HandoffRequest（目标操作）绑定change/adoption/decision identity、predecessor可空、new Definition revision/hash/startup input、successor intent/target RunID、expected slot/handoff generation、原授权/新授权范围、预算与effect责任引用。Orchestrator及各effect owner提供：

- 受影响dispatch停止及quiescence/drain事实、owner实际revision/fence；不能只提供日志里“已停止”
- 已知/在途/unknown operation集合、具体冲突范围、当前reservation成本、原Run/owner事实引用
- 对每项可能与后继冲突的effect，给出已确定完成/未发生/已对账的可信receipt，或足以阻止旧动作到达新范围的隔离/fencing证明
- 预算视图按原始consumption identity聚合confirmed和unknown-reserved；后继不能借新Run重新获得项目累计额度，也不能重复记账同一结算

unknown并非一律能安全运行，也不承诺等它必然查明：冲突域无法确定或无可信隔离时阻塞相关新effect。隔离证明仅允许不冲突动作，不把unknown改成失败/零成本；后续late receipt继续落原账并更新责任视图。各能力精确冲突域/证据及解除规则引用Core和组件具体合同。

### 7.2 跨Run冲突域和可接受proof

本节是跨Run交接proof的唯一详细定义；普通effect状态迁移/重试算法仍由Core维护。以下是**目标验收合同**，不是已实现能力清单，更不声称远端天然支持强幂等。没有对应owner可核验证明的能力按unsupported分支关闭，不能到实施时自由解释“安全”。

冲突集合由前驱的claimed/outcome_unknown或授权in_flight/uncertain执行事实，与后继拟议effect按`owner + canonical target/resource domain + effect scope + 实际资源revision`比较。不能证明不相交就按可能冲突；effectMode为none/ephemeral、lease过期、客户端超时、进程退出或用户点同意均不自动证明外部effect未发生。

**持久责任。** 原始execution/effect/cost与runtime operation receipt始终由Orchestrator ledger持久，实际能力owner只产出/查询自己的操作事实；Run仅承载既定opaque持久化，不解释语义。不能复制成新Run另一份已执行事实，也不要求File等无repository组件新增receipt仓库。H1/H3的ProducerEvidenceEnvelope由Workspace写入其handoff journal中的目标新增记录（尚不声称存在同名Go字段），只保存各owner原始事实refs、opaque检查/admission receipt、content hash、拟允许scope及handoff fence；它不复制effect/cost ledger，不接管原始操作真相，也不是未来后继的runtime acceptance。这个明确的pre-activation持久位置不依赖后继Run已物化或runtime存在。H6/A6后继Orchestrator初始化后才在自己的runtime aggregate持久barrier view/SuccessorBarrierAcceptance，并逐effect gate；原Run已terminal时读取其冻结快照；迟到receipt和成本结算写入同一Orchestrator owner-scoped操作/consumption身份下的append-only对账历史分区（目标恢复记录，通过既定Run opaque持久化载体保存），引用原ExecutionKey/receipt/cost identity及terminal seal。它是原账本的追加对账史，不是新支出账本或新的终态authority；只重算当前责任/barrier视图，不改冻结SM-2/3/4终验材料、旧closeout或旧Result。

跨Run证明分成两个阶段，不能让交接等待尚不存在的后继runtime：

- H1先持久producer evidence的原Run/operation/scope事实，活动前驱此时尚无最终Result时明确terminal refs待补，不伪造未来Result。H2完成真实终态后，H3重读当前owner依赖并封完整ProducerEvidenceEnvelope：predecessor RunID及exact ResultID/terminal snapshot、old ExecutionKey/operation/payload hash/claim fence/producer owner、unknown/receipt/cost refs、successor activation intent与H0预约的target RunID（尚非RunCreated）、new Definition、交接拟允许scope及真实resource revisions、proof kind/检查方法版本/观察时间/有效条件和原事实hash。H3不能用H1尚不完整/已过期观察通过；它不要求未来Orchestrator binding/revision，也不声称后继已接纳
- H6/A6在pending后继已完成lineage并合法激活后，由后继Orchestrator进行fresh workspace_full reconciliation，读取上述envelope及当前原owner事实，持久SuccessorBarrierAcceptance，补齐真实后继Run/runtime binding/revision、精确proof hash及允许/仍禁止effect集合。只有此事实满足当前操作条件后才允许drive/effect；H3证据不作为永久执行许可证
- H0的RunID预约只建立幂等身份，不建立Run生命周期实例。H4物化使用同ID；H6接纳不反向成为H3前置条件。无前驱时各前驱字段明确N/A，不能伪造Result；当前依赖改变使接受事实失效并重新关闭对应gate

#### 7.2.1 NC05-LATE terminal之后的受限对账接收合同

NC05-LATE是两个**独立具体目标接收合同**的组名，不是现有Go/topic声明，也不使用kind/payload万能消息。映射由组件目录给出；原草案ReceiveLateOperationReconciliation名称不再作为单一API。仅Orchestrator受理可信原producer的真实事实；Run提供owner-scoped opaque持久化，不解释/改写对账。terminal后这两个入口只追加原事实及预算责任投影，不恢复调度、不接受普通控制命令、不修改SM-1或冻结SM-2/3/4终验。

未知预算的分配/结算按原reservation identity或明确usage分段关联；不能只凭一个总费用数字推断全部其他未知调用已结清。若无法将新usage可靠归到原session/request和consumptionID，隔离为待核对事实并保持原reserved，不自行新建消费ID或ExecutionKey。Workspace及后继Run只读取同一源账的责任投影/refs，人工批准不能释放不明成本。

### 7.4 不可破坏的后继规则

- 一个具体change adoption + activation intent只能物化一个successor；每次线性继任必须核对当时真实前驱与Workspace活动资格。以后再次改约可产生下一段链，但不得把两个竞争后继都写成同一交接的获准结果
- no predecessor不补虚假历史Run；terminal predecessor不重开；旧合同不被new Definition覆写；普通同合同重试不必走NC04
- M3是Workspace首次创建的历史里程碑；后继启动需要当前NC01证书但不伪造“新建又完成一次/当时无历史Run”的M3回执
- 原Run unknown成本与效果始终由原记录负责，新Run携带责任引用与禁止冲突边界；不把旧账复制成新支出，也不把无值视为零
- 如果新Run启动前授权、readiness或交接失效，保留new Definition及已获批准事实，返回准确blocked phase；恢复只继续原意图。真正修改已批准候选才重新审查/approve
