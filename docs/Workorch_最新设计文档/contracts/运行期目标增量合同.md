## 2 CT-orchestrator-PreparePendingActivationTermination

- source=new / target=new；CF10；接收owner Orchestrator；唯一caller `blocks/run`；能力名同时涵盖pending以及已active但尚未建立Runtime aggregate的切点，名称中的Pending不是状态guard
- 目标文件：`internal/modules/kernel/orchestrator/pkg/events/administrative_closeout.go`
- 拟topic：`TopicPreparePendingActivationTermination = /orchestrator/command/prepare-pending-activation-termination`
- Command：`PreparePendingActivationTerminationCommand`；Result：`PreparePendingActivationTerminationResult`；返回行政上下文receipt，不授予业务执行许可

### 2.1 具体输入、presence与来源

| 字段 | 类型/必填语义 |
|---|---|
| SchemaVersion | uint32，恰为1 |
| WorkspaceID、RunID | 对应既有Run birth/物化身份，均非空；无Run时先按NC03同ID物化pending，不造dummy Run |
| CancellationIntentID、CancellationIntentHash | Run已持久的明确取消intent；均非空，同ID异hash冲突 |
| ExpectedRunRevision | uint64，非0；对应上述Run取消intent后像，不能拿UI旧revision |
| ActivationIntentID、PermitID、PermitHash、ReservationID、Generation | 原Start身份与Workspace已接纳permit/reservation；字符串非空、generation非0，不重新授权/消费一次Start |
| DefinitionRevision、DefinitionHash、StartupInputHash、BootstrapHash | 全部与Run冻结输入一致，不是当前默认配置；非空但不伪造SM-2 AuthoritySnapshotID/EvidenceRevision |
| InitializationFence、DispatchAdmissionFence | Run/Orchestrator该Run受控writer fence的非零token；不是caller任意数字；接收方必须核验当前资格 |
| SourceAuthorizationRef、Reason | 明确Cancel或已冻结policy对这次精确撤销的取消映射；非空，普通资源失败/网页关闭不构成合法取消 |
| BudgetLiabilityRefs | 有界原consumption/reservation引用列表；空列表仅在接收方独立证明原账确无责任时成立，不表示未查询 |

Orchestrator在同Run initialization/dispatch writer fence内，核验Run birth、初始化提交标记/opaque generation、authoritative dispatch/claim inventory与既有operation授权。未找到aggregate/receipt、空列表、timeout、lease到期都不是未提交证明。接收方生成并持久`ZeroBusinessAdmissionProof`：原Run、两个fence、inventory来源/版本/hash、观察revision、证明方法版本1及`NoBusinessAdmissionCommitted=true`；该bool只有完整owner证明成功后才能写，不能由caller直接提供。

### 2.2 原子承诺、结果臂与恢复

- 若已有可读完整Runtime aggregate：返回`ExistingRuntime`唯一臂（exact原Run、state ref/revision），caller转现有TerminationRequested，不重建上下文
- 若原birth/intent/fence一致且独立反证正常handoff尚未发生：expected Runtime revision=0，同fence CAS写`AdministrativeCloseoutRecord`；成功返回`Prepared`唯一臂（ContextRef、ContextHash、SchemaVersion=1、StateRevision、CancellationIntentID），重复同内容复用原receipt
- `AdministrativeCloseoutRecord`包含表中全部绑定、ZeroBusinessAdmissionProof、原预算责任refs及SM-4恢复/交付记录；RecordKind与authority-source固定。本variant永不转普通业务Runtime，不含SM-2 decision/authority/evidence/coverage或SM-3 session/attempt
- 无法证明、owner inventory失败或存在in-flight争议：返回`Blocked`唯一臂，包含typed原因、原identity、可重查owner ref与有界重试条件；不释放reservation、不provider、不改terminal。invalid/conflict/unsupported以typed error返回，不同时携带success臂
- 正常初始化先赢CAS：fresh-load进入ExistingRuntime；行政CAS先赢：正常初始化看到administrative_only必须拒绝。不能因重试换RunID或重置generation
- 上下文存在后由Core明确SM-4步骤保存TerminationRecord，再独立CAS封行政material；仅cancelled，不得failed/success。交付仍为Result→Workspace→Run exact ACK；合法pending/active取消分别走Run现有状态机对应terminal出口的目标扩展
- crash/丢回复后查询原Run opaque context/ref/hash；不能重发provider来“补出正常aggregate”。版本未知/结构损坏fail-closed，只能受控运维修复

### 2.3 三owner终态identity的目标扩展

`AdministrativeTerminalMaterialIdentity`固定SchemaVersion=1、AuthoritySource=RunAdministrativeIntent，并含WorkspaceID/RunID、DefinitionRevision/Hash、ActivationIntentID、CancellationIntentID/Hash、AdministrativeContextRef/Hash、Generation、TerminalMaterialID/Hash、Outcome=cancelled及原预算责任hash。所有字段必填；此variant没有SM-2 AuthoritySnapshotID/EvidenceRevision，字段空值只能由该variant明确区分，不允许向旧business variant填写占位值。

Result/Workspace/Run各自现有concrete terminal delivery合同均需明确版本化typed行政分支校验，ACK回显同一identity/material hash及原ResultID。Material不授coverage credit、不清除原义务；slot释放仍等待完整ordered ACK与适用post-terminal assertions；仅有后继场景要求双端lineage，普通无后继行政取消不要求SuccessorRunID。旧接收方必须返回unsupported，不能把缺业务identity当合法旧格式。该扩展影响现有CT-result-ResultFactTerminalDelivery、CT-workspace-WorkspaceFactTerminalDelivery、CT-run-RunFactTerminalDelivery；原business分支仍保留完整旧guard。

验证：VS-NC03-CANCEL、VS-V03/04/06/10/11/12/30/31/39；必须包含版本99、normal-init与admin-init竞态、active-before-A6、单ACK丢失以及没有明确取消依据的反例。具体fixture仅[验收规格](../validation/验收规格.md)维护。

## 3 CT-orchestrator-ReceiveLateOperationReceipt

- source=new / target=new；CF06/CF09；接收Orchestrator；caller仅原sealed operation所绑定的File/Git/Shell/SSH/Web/MCP owner，不能另一owner代写
- 目标文件`internal/modules/kernel/orchestrator/pkg/events/late_operation_receipt.go`
- 拟topic `TopicReceiveLateOperationReceipt = /orchestrator/command/receive-late-operation-receipt`
- Command `ReceiveLateOperationReceiptCommand`：SchemaVersion=1；WorkspaceID、OriginalRunID、DispatchID、OperationID、ExecutionKey、Fence>0；OriginalTerminalSealRef/Hash；ProducerFactID、ProducerFactHash；原owner exact typed RuntimeOperationReceipt；原ConsumptionID列表（确无费用才合法空）
- 以上identity/ref/hash均非空；receipt own ExecutionKey/Fence/OperationID/target/payload与原sealed记录一致，ProducerFactHash绑定规范编码完整fact。OriginalRun必须已terminal且seal一致；非terminal仍走既有CommitRuntimeOperationReceipt，不用此入口绕过正常流程
- 接收方必须核验原owner、原effect事实与receipt schema；late fact只能补充/结算原责任，不创建新执行，不移植为后继Run的effect，不授当前CWI credit。unknown不能仅靠caller宣称改成accepted
- Result `ReceiveLateOperationReceiptResult`：OriginalRunID、ProducerFactID/Hash、AppendRevision、AppendRecordRef/Hash、Disposition（appended或duplicate），均匹配原fact。相同fact ID/hash返回原receipt；同ID异hash/conflicting final receipt返回conflict，原记录不动
- 以原Run owner-scoped append partition独立CAS，单次提交追加fact、processed identity与原consumption settlement delta。终态后的标准OperationReceiptObserved不再适用；目标private event为LateOperationReceiptObserved（SM-4 only），完整写域引用Core
- 丢回复由Orchestrator计算原ProducerFactLookupHash，经Run QueryRuntimeLateSettlement的专用lookup读取原entry/ref/revision/hash；不是让调用方访问repository。并发appendRevision冲突fresh-load再核对，不能重放原effect。unsupported/坏schema/fence/owner错误拒绝且保留unknown责任。查询不到fact不能作为原effect未发生证明

## 4 CT-orchestrator-ReceiveLateProviderUsage

- source=new / target=new；CF05/CF09；接收Orchestrator；唯一事实caller LLM owner；Workspace无Run authoring账不走本合同
- 目标文件`internal/modules/kernel/orchestrator/pkg/events/late_provider_usage.go`
- 拟topic `TopicReceiveLateProviderUsage = /orchestrator/command/receive-late-provider-usage`
- Command `ReceiveLateProviderUsageCommand`：SchemaVersion=1；WorkspaceID、OriginalRunID、LogicalRequestID、RequestSessionID、ProviderRequestIdentity、RequestHash、ConfigurationRevision、ConsumptionID；OriginalTerminalSealRef/Hash；ProducerFactID/Hash；ProviderUsageFact（原provider/model、submitted、稳定SourceUsageIdentity、UsageSequence、UsageSegmentID、计量维度/单位与实际usage）与ObservedAt
- SourceUsageIdentity、UsageSegmentID非空，UsageSequence从1开始且同consumption/segment单调；ObservedAt为provider实际观察UTC时间，不能以当前接收时刻替换。所有identity/hash/revision均非空；OriginalRun与原logical request/session、provider request/hash/config、consumption对应。没有OperationID/ExecutionKey/dispatch fence；纯LLM session不得为了满足operation协议造dummy operation
- provider usage按原账已有计量维度精确校验，负值、NaN/Inf、单位变化、错配置、同fact异值拒绝。去重同时检查ProducerFactID/Hash以及原consumption+SourceUsageIdentity+UsageSequence+UsageSegmentID，换ProducerFactID重复同usage也不能再计；同usage identity异值冲突。ExpectedAppendRevision由Orchestrator在fresh-load后内部取得，不要求provider猜该版本；接收后在同CAS保存ObservedAt与原usage分段绑定。未知usage保持reserved；迟到confirmed替换该consumption的reserved结算视图，不再加一笔“新调用费用”
- Result `ReceiveLateProviderUsageResult`：OriginalRunID、ConsumptionID、ProducerFactID/Hash、AppendRevision、AppendRecordRef/Hash、Disposition（appended或duplicate）；互斥错误处理与前节相同，但不复用OperationReceipt DTO
- 目标LateProviderUsageObserved独立SM-4 append事务；不得改旧SM-2/3账/terminal材料，不触发provider重发。追加历史保留原unknown与迟到事实，当前责任/barrier预算视图按同consumption派生confirmed取代reserved；原账不是新Run再生额度

## 5 CF09目标opaque append持久接线

前两项late事实仍由Orchestrator拥有语义，通过Run owner持久边界新增专用opaque append分区保存；当前普通Runtime存储已使用typed RuntimeStateRecord，不能将其误写成既有opaque byte record。为了不让现有StoreRuntimeStateRecord覆盖已封存aggregate，本版选择新增两个concrete Run接收能力，禁用“更改旧aggregate再保存”的替代路线：

| 目标合同ID | topic/Command/Result | 真实能力边界 |
|---|---|---|
| CT-run-StoreRuntimeLateSettlement | TopicStoreRuntimeLateSettlement=`/run/command/store-runtime-late-settlement`；StoreRuntimeLateSettlementCommand / StoreRuntimeLateSettlementResult | 仅kernel/orchestrator；独立append CAS，不能写SM-1或旧runtime材料 |
| CT-run-QueryRuntimeLateSettlement | TopicQueryRuntimeLateSettlement=`/run/command/query-runtime-late-settlement`；QueryRuntimeLateSettlementCommand / QueryRuntimeLateSettlementResult | 仅kernel/orchestrator；读取原partition版本与opaque记录，返回detached值 |

目标文件统一`internal/modules/blocks/run/pkg/events/runtime_late_settlement.go`。Store输入：WorkspaceID/RunID、SchemaVersion=1、ExpectedAppendRevision指针（非nil；0只允许首次create-if-absent）、AppendRevision（恰expected+1）、PreviousRecordHash（首次为空，其余必须匹配）、RecordHash、OpaqueAppendRecord（≤1 MiB规范编码immutable字节；这是目标工程单record上限）、RuntimeTerminalSealRef/Hash、WorkspaceRetirementFence。scope/ref/hash必须非空且与Run原terminal identity一致；retired/purge fence不合法时拒绝。超过1 MiB必须typed oversize拒绝，不截断、不丢unknown责任、不自动放宽。大receipt原文由原事实owner按已有受限存储保存，append只存可核验immutable ref/hash及必要有界事实；若owner不支持稳定读取/校验则blocked，不能擅自降低业务义务。Run不解释usage/effect语义，但核验scope、链hash、revision与物理写入资格；Orchestrator提交前验证record完整语义。禁止把该字节载体用于任意owner可变共享数据。

Query输入WorkspaceID/RunID、ExpectedTerminalSealRef/Hash；读取selector只能三选一：ExactAppendRevision、ProducerFactLookupHash、SourceUsageLookupHash，全空表示读latest。非空selector必须唯一，hash精确绑定原Run/producer fact或原consumption/source usage identity+sequence+segment；不同selector不做模糊合并。Result用Found↔Record是否存在的明确互斥关系；存在时返回原SchemaVersion/AppendRevision/RecordHash与detached opaque值，不存在不授权重做effect。Store另含ProducerFactLookupHash（必填）与SourceUsageLookupHash（仅provider usage必填，operation为空），均由Orchestrator按目标schema=1规范前像计算；它们是该专用opaque分区的去重键，不是开放key/value袋。Run在同一物理CAS中提交entry和两类索引的opaque ref/hash，故crash后能查原fact，换ProducerFactID重复同source usage也不能再结算；同索引异recordHash冲突。Store成功返回实际AppendRevision/RecordHash及原seal；丢回复query精确revision/hash。物理Run记录CAS可在不改变semantic append前像时有界rebase；appendRevision冲突由Orchestrator fresh-load处理。

`RuntimeLateSettlementAppendRecord`归Orchestrator语义owner，固定SchemaVersion=1、OriginalRun/TerminalSeal identity、AppendRevision/PreviousRecordHash、一个具体OperationReceiptEntry或ProviderUsageEntry（恰一臂）、ProducerFactID/Hash、processed identity及原consumption结算delta；ProviderUsageEntry同时保留SourceUsageIdentity、UsageSequence、UsageSegmentID和ObservedAt。该设计类型是有限Runtime对账记录，不是shared business command。完整base账、SM-2/3、terminal seal/material/Result不可改；purge/retirement后不得通过append复生。支持旧terminal数据必须其原seal与consumption身份仍可验证，否则拒绝，不自动回填假identity。

验证：两个late入口分别VS-NC05-LATE-OP/VS-NC05-LATE-USAGE和VS-V03/04/06/10/11/15/34/39/41；包含version99、nil expected revision、同fact异hash、duplicate不重复消费、reserved→confirmed替换而非相加、purge并发、没有dummy operation的provider-only事实。验收最终case ID及细节以唯一验收规格为准。
