# Runtime V2 与强类型事件合同收口总结

日期：2026-07-14  
状态：代码收口完成，作为后续组件开发与审计约束

## 1. 收口目标

本次收口以 Runtime V2 为唯一运行架构，清理组件交互中的动态合同、历史兼容层和重复执行路径，使组件职责、事件所有权、类型边界及运行状态推进路径具备单一权威来源。

具体目标如下：

1. 全面切换至 Runtime V2，不再维护 Runtime V1 的执行与兼容能力。
2. 统一组件间通信机制，Module 与 Block 之间只能通过 `magicCommon.EventHub` 交互。
3. 将内部事件合同改为静态具体类型，禁止通过动态数据结构传递业务信息。
4. 明确事件合同所有权：投递组件负责定义完整的 command、data 和 result 类型。
5. 消费组件只订阅实际需要的 command，并直接导入投递组件公开的 `pkg` 合同。
6. 删除通用封装、动态转换、兼容回退和重复实现，形成单一执行链路。
7. 保持 kernel、orchestrator 等核心运行时功能中立，不引入具体业务领域或工具实现逻辑。

## 2. 组件职责定位

### 2.1 Module

- 承担涉及多个组件协作的业务编排。
- 允许管理自身状态。
- 与其他 Module、Block 的交互只能通过 EventHub。
- 不得通过内部实现包、共享可变对象或直接方法调用绕过事件边界。

### 2.2 Block

- 只承担一个独立组件能力。
- 允许管理自身状态。
- 对外能力通过自身定义的 EventHub 合同暴露。
- 不得承担跨多个组件的业务编排职责。

### 2.3 Initiator

- 只提供单一、无状态的基础启动或装配能力。
- 不管理业务状态和运行状态。
- 不承载业务决策、流程编排或持久化职责。

## 3. 组件交互约束

1. Module 与 Block 之间的跨组件交互必须通过 EventHub 完成。
2. 组件不得直接依赖其他组件的 `biz`、`internal` 或具体实现对象。
3. 组件不得通过共享可变状态、回调注册或直接服务调用形成隐式耦合。
4. 投递组件是事件 Topic、command、data、result 及错误语义的唯一合同所有者。
5. 消费组件必须直接导入投递组件公开的事件合同，不得自行复制镜像 DTO。
6. 消费组件只订阅自身实际需要的 Topic，不得使用未知 Topic 或通用消息兜底处理业务事件。

## 4. 事件合同要求

每项事件能力必须由投递组件明确提供：

- 独立且稳定的 Topic。
- 具体的 command 类型。
- 具体的请求 data 类型。
- 具体的 result 类型。
- 明确的错误返回语义。
- 必要的来源标识、资源身份、生命周期、幂等及关联字段。

消费组件必须：

- 使用投递组件公开的 `pkg/events` 或合同包。
- 按需订阅具体 Topic。
- 使用具体 command、data、result 类型处理消息。
- 通过静态类型断言确认响应，不依赖字段名猜测数据结构。
- 在合同不匹配时直接返回明确错误，不得降级为动态载荷处理。

## 5. 禁止的实现模式

以下模式不得用于内部组件交互：

- 使用 `map[string]any`、`[]any` 承载 command、data、result 或业务载荷。
- 在 EventHub Envelope 或其他内部消息信封中保留业务含义的 `any` 字段。
- 通过 JSON marshal/unmarshal 完成内部组件间的类型转换。
- 使用 `reflect.Type`、字符串类型名或运行时反射驱动消息合同。
- 使用通用 `MessageContract` 动态注册业务消息。
- 使用 `eventcontract.SubscribeCommand` 等通用订阅包装隐藏真实合同。
- 使用 MagicHub 或其他通用 Envelope 承载动态 command、data、result。
- 对未知 Topic 回退为 map、JSON 或通用消息处理。
- 以“外部协议兼容”为理由在内部保留动态合同路径。
- 在生产代码中保留 Runtime V1/V2 双写、双读或双执行路径。
- 由消费组件重新定义投递组件的事件合同。
- 使用聚合 CLI command/result 承载多种语义不同的操作。

JSON 仅允许存在于真正的外部协议边界，例如 HTTP 请求响应、配置文件或持久化格式。外部数据进入内部组件后必须转换为具体领域类型，内部返回结果也必须在外部边界处再进行协议编码。

## 6. CLI 合同收口要求

1. 删除聚合式 `/cli/command` 合同。
2. 删除通用 `CLICommand`、`CLIResult` 和 `clicore`。
3. 每项 CLI 操作使用独立的具体 command/result Topic。
4. CLI 适配层只负责参数解析、调用具体合同和输出展示。
5. CLI result 不得通过动态字段承载不同操作的返回结构。
6. CLI 与服务内部的交互必须复用组件公开的强类型事件合同，不得建立平行协议。

## 7. Runtime V2 收口要求

1. Runtime V2 是唯一运行入口、唯一状态推进路径和唯一执行合同体系。
2. 删除 Runtime V1 的执行、维护、迁移、备份和兼容代码。
3. shell、file、git、SSH、Web、MCP 等运行操作使用各自独立的具体合同。
4. orchestrator 只负责运行状态机、调度、治理和结果汇聚。
5. 工具参数解释、执行行为及工具结果类型归所属 Block 管理。
6. operation 返回结果使用具体类型处理，不得经过通用 map、JSON 或反射转换。
7. 同一运行状态只能存在一个权威写入路径。
8. 投影、展示和外部协议层只能读取或转换权威状态，不得反向决定运行状态。

## 8. 22 个组件 README 要求

组件根目录下的 `readme.md` 只应包含：

1. 组件承担的功能。
2. 与其他组件的交互关系。
3. 对外投递及消费的事件合同。
4. 组件边界和实现约束。
5. 已确认但尚未闭环的能力缺失。

`readme.md` 不应包含临时实施计划、过程日志、重复架构背景或已经失效的兼容说明。组件代码实现、事件合同和 README 中的职责声明必须保持一致。

## 9. 代码处理要求

后续新增或修改代码时必须遵循以下处理顺序：

1. 首先确认功能应归属 Module、Block 还是 Initiator。
2. 明确负责投递事件的组件，并在该组件公开合同包中定义具体类型。
3. 由消费组件直接订阅具体 Topic 并导入投递组件合同。
4. 删除被新合同替代的动态载荷、通用包装和兼容路径。
5. 为合同投递、消费、错误语义和类型不匹配补充回归测试。
6. 同步核对组件 README，确保职责、交互和合同说明与代码一致。
7. 执行静态扫描，确认没有重新引入 map、JSON、反射或 `any` 事件桥接。

## 10. 验收标准

本次及后续同类收口需要同时满足：

- Runtime V1 生产代码无残留。
- Module、Block 跨组件调用全部经过 EventHub。
- 事件 command、data、result 全部为具体类型。
- 内部事件链路不存在 map、JSON、反射或 `any` 动态桥接。
- 不存在 MagicHub、通用 sender、通用 subscriber 等兼容层。
- 不存在旧 CLI 聚合合同和动态 CLI result。
- 22 个组件的职责、代码实现和 README 相互一致。
- 核心运行时保持业务中立。
- 相关合同回归测试完整。
- `go test ./... -count=1`、`go vet ./...`、格式检查和边界检查全部通过。

## 11. 最终原则

> 组件定义自己的能力和事件合同，跨组件只通过 EventHub 使用具体类型交互；Runtime V2 是唯一运行路径，内部不保留动态合同、历史兼容回退或平行执行链路。
